## 0. 本文档的地位与 v2.0 的增量

### 0.1 v1.0 做对了什么

`20260910_目标架构.md`(v1.0)用四个设计回答了三个问题:双形态如何装配(§2)、运行时资源如何统一管理(§3)、运维如何获取全模块数据(§4),并在 §5 埋下 S3 扩展点契约。

它有两个**底座级的正确基因**,v2.0 完整保留并强化:

1. **扩展点 = 治理能力的接入契约**(v1.0 §5.2)。不是"注册表",而是"接入即继承治理"。这直接导出 S3 的核心性质:**新增工具对平台零改动**。
2. **约束由机器执行**。`maven-enforcer` 禁依赖、防线 2 测试守护资源登记、`matchIfMissing` 默认 LOCAL——v1.0 已经理解"防劣化的本质是机器拦截"。

### 0.2 v1.0 没解决什么

v1.0 的四项设计全部落在**「可治理」这一根柱子上,而且只是它的一半**——"看得见"(资源视图/指标/健康/traceId)。三块关键拼图缺失:

| 缺失 | 后果 | v2.0 章节 |
|---|---|---|
| **工业化**:质量门禁、测试基座、发布回滚 | 防劣化的自检机制**自己没有被测试**——守护者脚下是空的 | §2 |
| **可演进**:ADR、契约版本、弃用生命周期、迁移范式 | 能安全地**加**工具,但改/删一个契约时无人告诉你谁会挂 | §3 |
| **防劣化**:覆盖面只有 1 条依赖规则 + 9 类资源 | 质量、契约、迁移、架构腐化四条更重要的防线全空 | §5 |

### 0.3 v2.0 的总判据(唯一一条)

> **新增一个工具模块,平台改动行数 = 0;故意违反任一约束,CI 必须变红。**

前半句来自 v1.0(S3 验收标准),后半句是 v2.0 的新增。**判据必须能被机器验,不能被人评审。**

阅读约定:文中 `[目标]` 为终态设计,`[现状]` 为当前代码基线,所有现状结论可在 `当前实现能力清单` 中复核。

## 1. 架构总纲:底座能力模型

### 1.1 四根支柱

| 支柱 | 本质 | 检验刻度(可测量) |
|---|---|---|
| **工业化** | 交付可重复、质量可拦截 | CI **不跳过测试**;覆盖率/静态分析/漏洞扫描有阈值;测试金字塔;发布可回滚 |
| **可演进** | 变更成本不随时间上升 | 能安全地**加 / 改 / 删**:扩展点 + 契约定版策略 + 迁移范式 + ADR |
| **可治理** | 看得见 **且** 管得住 | 资源总账、指标健康日志(看得见) + 鉴权、审计、配额隔离(管得住) |
| **防劣化** | 违背约束时**机器拦截** | 约束 → 拦截矩阵全覆盖;每一条约束都有负向验收用例 |

四根柱子**互相支撑,不可偏科**。最典型的偏科是:设计了一套精美的自检体系(防劣化),却运行在"跳过测试"的 CI 上(工业化缺失)——此时自检体系本身无法被信任。

### 1.2 能力成熟度分级

| 级别 | 判据 | DevNest 现状 |
|---|---|---|
| **L0 能跑** | 功能可用,无自动化 | — |
| **L1 可构建** | 一键构建 + 启动冒烟 | ✅ **当前在此**(CI 有构建与冒烟) |
| **L2 可拦截** | 测试被强制执行,质量有阈值 | 目标 §2 |
| **L3 可演进** | 契约与迁移受治理,变更可安全落地 | 目标 §3 |
| **L4 可治理** | 全维度可观测 + 闭环防劣化,新工具零改动接入 | 目标 §4/§5 |

**v2.0 的目标是把 DevNest 从 L1 推到 L4。** 落地的顺序必须是 L1→L2→L3→L4:**跨越 L2 直接建 L4 是无效的**——L4 的所有"自动拦截"都依赖 L2 的测试与门禁作为执行载体。

### 1.3 目标形态

**双形态**(继承 v1.0 §1.1):一个构建产物,**两种装配**;形态由启动参数决定,**不由代码分支决定**。

```
                    ┌─────────────────────────────┐
                    │   同一份 devnest-boot.jar    │
                    └──────────────┬──────────────┘
                                   │
              devnest.mode=local(默认)    devnest.mode=server
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                          ▼
    ┌───────────────────┐                     ┌───────────────────┐
    │  LOCAL 形态        │                     │  SERVER 形态       │
    │  仅回环、单用户      │                     │  内网、多用户       │
    │  无鉴权、全量可见    │                     │  完整鉴权、按归属可见 │
    │  桌面壳拉起         │                     │  浏览器访问         │
    └───────────────────┘                     └───────────────────┘
```

**工具巢穴**(继承 v1.0 §1.2):平台提供治理,工具提供业务,**新增工具对平台零改动**(§5.1 C11 把它变成可测的 fitness function)。

## 2. 支柱一:工业化

> **这是 v2.0 最大的增量,也是当前最大的短板。** v1.0 全文未提。

### 2.1 现状

| 刻度 | 事实 | 证据 |
|---|---|---|
| 构建可重复 | 一键打包 + CI 打包,jlink 模块清单单一事实源 + 回归自检 | `build-app.ps1`、`.github/workflows/build-app.yml` ✅ |
| **质量门禁** | CI 与本地**均为 `mvn package -DskipTests`**;无 JaCoCo、无 Sonar/SpotBugs/Checkstyle、无 OWASP dependency-check | CI `:127`、`build-app.ps1:46` ❌ |
| **测试规模** | **全库 5 个测试类**;无 `@SpringBootTest`、无 Testcontainers、无测试基类、无 AssertJ;`tunnel`/`console`/`pipeline` **零测试** | ❌ |
| 发布回滚 | 无回滚脚本、无回滚流程文档 | ❌ |

**两个必须点名的隐患:**

1. **守护者无保护**(自指漏洞)。v1.0 §3.5 防线 2 要"提供测试基类,断言资源类型完整性"——但当前**连测试基类都不存在**,且 CI 跳过测试。防线 2 是空中楼阁。
2. **测试库与生产库方言分裂**。测试用 H2(`MODE=MySQL`),生产用 MySQL 8。`MODE=MySQL` 是**模拟**,不是 MySQL——DDL、类型、函数、锁行为均可能不同。**"测试绿了"不能推出"生产没问题"。**

### 2.2 质量门禁(四道,缺一不可)

`[目标]` 把 `mvn package -DskipTests` 改为 `mvn verify`,并在 CI 强制:

| # | 门禁 | 工具 | 阈值(初值,可调) | 拦截什么 |
|---|---|---|---|---|
| G1 | 单元/集成测试 | Surefire + Failsafe | 失败即红 | 功能回归 |
| G2 | 覆盖率 | JaCoCo | 行覆盖 ≥ 60%,**增量 ≥ 80%** | 新增代码无测试 |
| G3 | 依赖收敛与漏洞 | enforcer `dependencyConvergence` + OWASP dependency-check | CVSS ≥ 7 即红 | 版本漂移、已知漏洞 |
| G4 | 架构约束 | ArchUnit | 违规即红 | 分层破坏、形态语义散落 |

> **G2 用"增量覆盖率"而不是"总量覆盖率"**:总量阈值在存量代码上会长期锁死,开发者只会写无意义测试凑数;**增量阈值才能真正阻止新代码无测试**。

### 2.3 测试金字塔与测试基座

`[目标]` 五层,现状只有 L1 的 5 个孤立用例:

| 层 | 内容 | 工具 | 现状 |
|---|---|---|---|
| L1 单元 | 纯逻辑,无 Spring | JUnit 5 + Mockito + AssertJ | ⚠️ 5 个,够用即可 |
| L2 切片 | Controller / Repository 单层 | `@WebMvcTest` / `@DataJpaTest` | ❌ 0 |
| L3 集成 | 真实中间件 | **Testcontainers(MySQL 8 + Redis)** | ❌ 0 |
| L4 契约 | SPI 装配契约、平台治理契约 | 自定义断言 | ❌ 0 |
| L5 端到端 | 启动冒烟 | CI 已有 | ✅ |

**L3 是重点**:引入 Testcontainers 跑**真实 MySQL 8**,消除 §2.1 的方言分裂。这是"测试能否代表生产"的底线。

`[目标]` 提供测试基座(它是 v1.0 防线 2 的前提):

```java
// core/test/  [目标]
public abstract class ResourceRegistryTestBase {
    /** 断言:登记表非空,且资源类型集合 == 预期集合。子类声明 expectedResourceTypes() */
    @Test
    void allResourceTypesRegistered() {
        Set<String> actual = registry.countByType().keySet();
        assertThat(actual).containsExactlyInAnyOrderElementsOf(expectedResourceTypes());
    }
}
```

### 2.4 构建与发布可回滚

| 能力 | 目标设计 |
|---|---|
| 版本可追溯 | 构建产物内嵌 `git commit` + 构建时间(Spring Boot build-info),`/actuator/info` 可见 |
| 数据库可回滚 | 见 §3.4 expand-contract:每次迁移**前向兼容**,回滚 = 回退应用版本而非回退 schema |
| 回滚流程 | `docs/ops/发布与回滚.md`:回滚判据、命令、验证步骤(校验 `/actuator/health` + 资源快照) |
| 桌面壳与 jar 同版本 | jlink 模块清单已是单一事实源(✅),`build-app.ps1` 保证 jar 与 JRE 同批产出 |

### 2.5 验收

| 验收项 | 验证方式 |
|---|---|
| 测试被强制执行 | 故意删一个断言 → CI **红** |
| 覆盖率有约束 | 提交零测试的新类 → 增量覆盖率门禁**红** |
| 漏洞可拦截 | 引入一个已知高危版本 → dependency-check **红** |
| 方言一致 | 仓储层测试跑在 Testcontainers MySQL 上,而非 H2 |

## 3. 支柱二:可演进

> "可演进"不等于"能加东西"。**加得进、改不动、删不掉,是演进的反面。**

### 3.1 现状

| 刻度 | 事实 | 判定 |
|---|---|---|
| 扩展点 | v1.0 §5 `DevNestTool` 设计正确 | ✅ 设计有,未实现 |
| 契约版本 | 无 `/v1/`、全库 `@Deprecated` **0 命中**、无弃用策略 | ❌ |
| 迁移演进 | Flyway 11 个脚本**全单向 forward**,无 `U__`/`R__`,无 expand-contract 规范 | ⚠️ |
| 决策追溯 | **无 ADR**,决策埋在长文档叙述里 | ❌ |

### 3.2 ADR:决策必须可追溯

`[目标]` 建立 `docs/adr/`,采用 MADR 精简模板:

```
docs/adr/
  0001-单进程多模块而非微服务.md
  0002-登记但不接管资源释放.md
  0003-形态与 profile 正交.md
  0004-不做 URL 版本化.md
```

每条决策记录四要素:**背景 / 备选方案 / 决策 / 后果**。

**为什么这是"可演进"的核心**:架构的可演进性来自**不重复犯错的决策**。没有 ADR,半年后没人知道"为什么不做分布式",于是有人重新提,重新论证,或更糟——**悄悄做了**。v1.0 §7 的边界声明本质就是 ADR,只是没编号、不可检索、无法被引用。

### 3.3 契约版本与弃用生命周期

**先明确一个经过考虑的否定:`不做 URL 版本化(不加 /v1/`)。**

理由:DevNest 是**单实例内网工具平台**,前后端(桌面壳/浏览器 UI)与后端**同批发布、无第三方消费者**。URL 版本化的成本(路由分叉、双份文档、长期维护)大于收益。**URL 版本化是为"无法协同发布的独立消费者"准备的,此处没有这个消费者。**

替代方案是**字段级兼容策略**,这是更适合本场景的契约治理:

| 变更类型 | 策略 | 说明 |
|---|---|---|
| 新增字段 | **允许**(直接做) | 消费者必须容忍未知字段(Jackson 默认行为) |
| 新增枚举值 | **允许,但消费者必须容错** | 前端不得对未知枚举值崩溃 |
| 修改字段语义 | **禁止** | 必须新增字段并弃用旧字段 |
| 删除字段 | **两阶段** | 先 `@Deprecated` 标记 + 双方停用,至少一个发布周期后才可删 |

`[目标]` 弃用规范(把"删除"变成有约束的动作):

```java
// [目标] 弃用必须声明 since 与 forRemoval,否则视为违规
@Deprecated(since = "1.2.0", forRemoval = true)   // ← ArchUnit 校验此注解必须带 since
public String oldField;
```

> 现状全库 `@Deprecated` **0 命中**——不是因为没有需要弃用的东西,而是因为**没有弃用机制**,旧结构只会被默默留着或被直接删除。

### 3.4 数据库迁移演进范式:expand-contract

`[现状]` 11 个 Flyway 脚本(`V1`–`V11`)全部是**单向 forward DDL**,无 `U__`/`R__`,无迁移范式。

`[目标]` 引入 **expand-contract 三段式**,把"破坏性变更"拆成三个前向兼容步:

```
场景:把 datasource.visibility 从 VARCHAR 改为 ENUM

① EXPAND   V12__add_visibility_enum.sql     新增列 visibility_enum,可空,旧代码不受影响
② MIGRATE  V13__backfill_visibility_enum.sql 回填数据;应用双写两列
③ CONTRACT V14__drop_visibility.sql          应用已不再读旧列,删除
```

**每条迁移必须满足"前向兼容":任何时候回退应用版本,新 schema 仍能被旧代码使用。** 因为回滚 = **回退应用版本**,而不是回退 schema——这才是"可回滚"在数据库层面的真正含义。

补充约束:
- 禁止在迁移中做 `DROP`/`RENAME`(除非已走完 contract 阶段);
- 长表回填必须与迁移解耦(迁移只建列,回填走独立任务),避免 Flyway 卡住启动;
- `docs/architecture/database-init.sql` 与 `V1` 的结构重复需消除(改为由 V1 生成,或明确标注为"仅参考")。

### 3.5 兼容性矩阵

`[目标]` `docs/ops/兼容性矩阵.md` 维护:应用版本 × schema 版本 × 前端版本的兼容区间。上线前核对,防止"新 jar + 旧库"这类错配静默启动。

### 3.6 验收

| 验收项 | 验证方式 |
|---|---|
| 决策可追溯 | 任一"不做 X"的决策能在 `docs/adr/` 找到编号 |
| 弃用受约束 | 新增一个无 `since` 的 `@Deprecated` → ArchUnit **红** |
| 迁移前向兼容 | 回退应用版本到上一版,新 schema 下**启动成功且功能可用** |
| 兼容矩阵有效 | 故意用"新 jar + 不兼容旧库"启动 → **启动自检失败** |

## 4. 支柱三:可治理

> 本章继承 v1.0 §2/§3/§4 并做三处修正,再补 v1.0 缺失的"管得住"部分(§4.4/§4.5)。

### 4.1 形态装配模型

**继承 v1.0 §2**:形态元注解、模块自描述自动配置、SPI 可覆盖装配契约、`ServerModeConsistencyCheck` 防退化自检(见 v1.0 §2.2–§2.4,此处不重复)。

#### 4.1.1 修正:形态与 profile 必须正交

`[现状]` `spring.profiles.active` **同时承担了两种语义**,这是架构耦合:

| 现有 profile | 实际语义 | 问题 |
|---|---|---|
| `dev` | 环境(开发:开 SQL 日志) | ✅ 环境 |
| `prod` | 环境(生产:MySQL) | ✅ 环境 |
| **`desktop`** | **交付形态**(桌面壳拉起 + H2 文件库 + 日志收敛) | ❌ **这是形态,不是环境** |

`desktop` 挂在 profile 上,导致"形态"这个正交维度被塞进"环境"这一维,两者强行绑定。后果:**想要"LOCAL 形态 + 生产日志级别"就必须新增 profile**,维度爆炸。

`[目标]` 两个维度正交解耦:

```
devnest.mode = local | server      ← 决定「装配」:装哪些 Bean(条件化),不影响任何环境值
spring.profiles.active = dev | prod ← 决定「环境值」:库、日志级别、绑定地址
```

- **形态注解只读 `devnest.mode`**,不读 profile(v1.0 §2.2.1 元注解已正确,此处明确禁止反向依赖);
- `application-desktop.yml` 退役:其内容(H2 文件库 + 日志收敛)拆为"LOCAL 形态默认环境",由 `devnest.mode=local` 触发,不再需要独立 profile;
- 保留 `application-dev.yml` / `application-prod.yml` 作为纯环境 profile。

**这同时解决了早期设计草稿引入的 `application-local.yml`/`application-server.yml` 命名冲突**——那组命名把形态又编码进了文件名,等于把刚解开的耦合重新系上。

#### 4.1.2 修正:鉴权锚点必须点名

`[现状]` `ActuatorSecurityConfig` 的最后一行的注释与实现:

```java
// ActuatorSecurityConfig.java:58-59  [现状]
// 业务 API 全部放行(依赖 CORS + WS TOFU + 127.0.0.1 绑卡)
.anyRequest().permitAll()
```

这行是**服务端形态必须替换的锚点**。它的前提("仅绑 127.0.0.1")正是 SERVER 形态打破的那一刀。v1.0 §2.3 只写了"鉴权:边界收敛 → 完整链路",**没有落到具体代码位置**。v2.0 明确:

`[目标]` 该行改为按形态装配的鉴权链:

```java
// [目标] SERVER 形态:业务 API 走完整鉴权;LOCAL 形态保持 permitAll(不牺牲本地零配置)
.anyRequest().access(serverMode ? authenticatedAndAuthorized() : permitAll())
```

### 4.2 资源统一管理

**完整继承 v1.0 §3**,包括:

- **登记 ≠ 接管释放**(各模块 `@PreDestroy` 保持原样,登记表只记账);
- `ManagedResource` 描述符(不强制资源类实现接口、禁止携带敏感值);
- `ResourceRegistry` 五个方法(register/updateState/unregister/snapshot/countByType);
- 9 类资源登记表(登记者 / 释放者不变 / 关键属性);
- 三重防漏登记防线(启动自检 / **测试守护** / 文档评审);
- 优雅关闭链路升级(资源状态同步 + 关闭报告)。

**修正一处 v1.0 的事实错误**:v1.0 §4.5 写"`SensitiveDataLogFilter` 已存在,可作为 traceId 的实现载体"。核实后该判断不成立——`SensitiveDataLogFilter` 是 **Jackson 响应体字段脱敏器**,源码注释自己写明"代码里手动 `log.info("xx={}", passwordStr)` 的泄露本 Filter 不能覆盖",它**接不进 MDC**。traceId 载体见 §4.3.4。

### 4.3 全维度可观测

**继承 v1.0 §4** 的资源视图 / 指标 / 健康三维设计(含 11 项指标命名 `devnest.<domain>.<metric>`、3 个 HealthIndicator、`/actuator/resources` 端点),并做三处升级:

#### 4.3.1 升级:traceId → traceId + spanId

仅 traceId 只能"串联",不能回答"哪一跳慢"。`[目标]`:

- 引入 **Micrometer Tracing**(Spring Boot 3.2 已内置桥接,不引入额外部署负担),自动产生 `traceId` + `spanId`;
- **明确边界:不部署 trace 后端(不做 Jaeger/Zipkin collector)**。追踪数据以"结构化日志 + 端点内联"方式可见,保持单实例轻量定位。**这是经过考虑的否定,不是遗漏。**

#### 4.3.2 升级:指标 → SLI/SLO

`[现状]` 指标只服务"看看数",不服务"是否达标"。`[目标]` 定义 4 条核心 SLI(单实例内网工具,不贪多):

| SLI | 定义 | 目标(初值) |
|---|---|---|
| 隧道建立成功率 | 成功 RUNNING / 发起连接 | ≥ 95% |
| SQL 执行成功率 | 非异常返回 / 总执行 | ≥ 99% |
| 接口可用性 | (1 − 5xx 率) | ≥ 99.5% |
| 就绪时间 | 启动到 `/actuator/health` UP | ≤ 15s |

SLO 用于**回归检测**:版本对比,任一 SLI 显著劣化即视为退化(接 §5)。

#### 4.3.3 修正:traceId 载体

`[目标]` 新建载体,**不复用 `SensitiveDataLogFilter`**:

1. 新增 `TraceIdFilter`(servlet `OncePerRequestFilter`),在入口生成/透传 traceId 写入 MDC;
2. **新增 `logback-spring.xml`**(`[现状]` 无该文件),pattern 增加 `%X{traceId:-} %X{spanId:-}`;
3. **虚拟线程不继承 `InheritableThreadLocal`**——这是最容易漏的点(Java 21 虚拟线程 + `threads.virtual.enabled=true` 已开启),异步任务必须**显式传递 MDC 上下文**,并用测试守护(见 §5)。

#### 4.3.4 修正:健康端点职责边界

`TunnelHealthIndicator` / `PoolHealthIndicator` / `ResourceRegistryHealthIndicator` 只反映**系统可用性**,不反映**单次业务结果**。`PipelineRunManager` 业务运行失败**不得**导致 `/actuator/health` DOWN(继承 v1.0 §4.4 的正确约束)。

### 4.4 安全纵深(v1.0 缺失)

> 治理 = 看得见 **+ 管得住**。v1.0 做到了"看得见",本节补"管得住"。

#### 4.4.1 鉴权

见 §4.1.2:业务 API 在 SERVER 形态下走完整鉴权,LOCAL 形态保持零配置。这是"双形态最容易做砸的地方"——**为服务端安全把本地体验拖下水是典型失败**(违反演进不变量 7)。

#### 4.4.2 审计(通用操作审计切面)

`[现状]` 仅有数据层 `sql_execution_log`(含 `operator`),**无通用操作审计**。

`[目标]` 新增审计事件模型 + 切面:

```
audit_event: id | operator | action | target_type | target_id | result | ip | trace_id | created_at
```

- 覆盖写操作(CRUD、执行、启停),`@Auditable(action="...", targetType="...")` 标注;
- `trace_id` 与 §4.3 打通:**一次操作的所有日志可经 traceId 聚合**;
- LOCAL 形态可关闭落库(避免本地噪音),SERVER 形态强制开启。

#### 4.4.3 密钥治理(含一处已发现的真问题)

`[现状]` `CryptoService` 密文格式 `base64(IV || CT || TAG)`,`KeyManager` 从 `%USERPROFILE%\.devnest\master.key` 载入 32B 主密钥。

**真问题:密文格式中没有 `keyId`,主密钥无法轮换**——一旦更换 master.key,**所有已加密的密码密文全部无法解密**,且没有版本号可做渐进迁移。单机自用时可接受(用户可以重录),但 SERVER 形态下这是**不可运维的设计**。

`[目标]`:

| 项 | 设计 |
|---|---|
| 密文自描述 | 密文头增加 `keyId`(如 `v1:` 前缀或结构化 `{keyId, iv, ct, tag}`),支持多密钥并存 |
| 密钥轮换 | 支持"新写入用新密钥,旧密文按 keyId 解密",提供批量重加密命令 |
| 密钥来源 | LOCAL:落盘文件(保持现状);SERVER:外部注入(环境变量 / 挂载卷),不落用户目录 |
| 禁止项 | 密钥值不得进入 `ManagedResource.attributes()`,不得进日志或审计事件 |

#### 4.4.4 供应链安全

`[目标]`:构建产出 **SBOM**(CycloneDX),依赖漏洞扫描进 CI(§2.2 G3),发布产物附校验和。`cyber-dependency` 与桌面壳的 jlink 裁剪共同构成供应链闭环。

### 4.5 隔离与配额(v1.0 缺失)

> 底座级的判据之一是:**一个工具故障,不得拖垮平台与其他工具。**

`[现状]` `resilience4j-spring-boot3` 在根 POM **声明但无任何模块引入、代码零使用**——典型的"已付成本无收益"。

`[目标]` 用 resilience4j 做**工具级/资源级隔离**(不是全局限流):

| 机制 | 应用点 | 目的 |
|---|---|---|
| Bulkhead | 每工具/每模块独立并发舱 | 一个工具打满线程,不耗尽全局虚拟线程池 |
| CircuitBreaker | 隧道重连、外部库调用、Redis 探测 | 故障快速失败,避免雪崩 |
| RateLimiter | 建隧道、执行 SQL、执行 Redis 命令 | 防误操作风暴(脚本刷接口) |
| TimeLimiter | 已有 `query-timeout-seconds=30` | 统一超时语义 |
| 背压 | 已有 `max-concurrent-runs=5`(pipeline) | 保持 |

**已有的配额基础**(✅ 保留):`max-pools=20`、`max-pool-size=8`、`leak-detection-ms`、`connection-timeout-ms`。

**新增**:`/actuator/health` 对"资源用量触顶"做 `PoolHealthIndicator` 预警(v1.0 已设计)。

### 4.6 验收

| 验收项 | 验证方式 |
|---|---|
| 形态与 profile 正交 | LOCAL 形态 + prod 环境可同时成立,无需新增 profile |
| 鉴权锚点生效 | SERVER 形态下未登录访问业务 API → 401;LOCAL 形态 → 直通 |
| 密钥可轮换 | 更换主密钥后,旧密文仍可解密,新写入用新密钥 |
| 审计可串联 | 一次写操作可在 `audit_event` + 日志中经 traceId 查到全链路 |
| 故障被隔离 | 人为让 tunnel 模块阻塞 → 其他工具 API 仍正常响应 |

## 5. 支柱四:防劣化

> **防劣化的本质是:约束必须由机器执行,而不是靠人自觉。** v1.0 已经理解这一点(见其 §3.5 防线 2),但覆盖面太窄——只有 1 条依赖规则 + 9 类资源登记 + 1 个形态校验。

### 5.1 约束 → 拦截矩阵(核心)

`[目标]` 每一条架构约束都必须有唯一的机器执行者。**没有执行者的约束不是约束,是愿望。**

| # | 约束 | 拦截手段 | 时机 | 现状 |
|---|---|---|---|---|
| C1 | 业务模块间零横向依赖 | `maven-enforcer` `bannedDependencies` | 构建 validate | ✅ 已实现 |
| C2 | 依赖版本收敛(无冲突版本) | `maven-enforcer` `dependencyConvergence` | 构建 validate | ❌ |
| C3 | 无已知高危依赖 | OWASP `dependency-check` (CVSS ≥ 7) | CI | ❌ |
| C4 | 分层依赖方向正确 | **ArchUnit**(core 不得依赖任何 impl 包) | CI | ❌ |
| C5 | 新增运行时资源必须登记 | `ResourceRegistry` 启动自检 + `ResourceRegistryTestBase` | 启动 + CI | 设计有 |
| C6 | SERVER 形态不得装配本地实现 | `ServerModeConsistencyCheck`(启动即失败) | 启动 | 设计有 |
| C7 | 覆盖率不下降 | JaCoCo **增量覆盖率** ≥ 80% | CI | ❌ |
| C8 | 契约向后兼容 | 契约测试(字段/枚举兼容用例) | CI | ❌ |
| C9 | 迁移前向兼容 | 迁移测试:旧版应用 + 新 schema 启动 | CI | ❌ |
| C10 | 形态语义不得散落 | **ArchUnit**:业务代码禁用裸 `@ConditionalOnProperty` | CI | ❌ |
| C11 | 新工具零改动接入治理 | **fitness function**:新增测试工具模块 → 其资源/指标/健康自动出现 | CI | ❌ |
| C12 | traceId 跨线程不丢失 | 测试:提交异步任务后断言 MDC 中的 traceId | CI | ❌ |
| C13 | 弃用标注完整 | ArchUnit:`@Deprecated` 必须带 `since` | CI | ❌ |

**C10 与 C13 是 v1.0 精神的延伸**:v1.0 说"业务模块不得直接用 `@ConditionalOnProperty`,必须用形态元注解"——但那只是**文档约定**。v2.0 把它升级为 **ArchUnit 断言**,违规即构建失败。**约定 → 断言,是防劣化的关键跃迁。**

### 5.2 负向验收:故意违反,CI 必须红

`[目标]` 验收方式从"功能达到了吗"改为"**退化会被发现吗**"。每条约束配一个**负向用例**:

| # | 负向用例(故意做错) | 期望 |
|---|---|---|
| N1 | 在 `core` 中 `import com.devnest.tunnel.*` | 构建失败(C1/C4) |
| N2 | 新增一个持有 `Map` 的资源容器但不登记 | 启动 WARN + CI 测试失败(C5) |
| N3 | SERVER 形态下装配 `LocalUserProvider` | **启动失败**并指明原因(C6) |
| N4 | 提交一个零测试的新类 | 增量覆盖率门禁红(C7) |
| N5 | 删除一个响应字段 | 契约测试红(C8) |
| N6 | 新增一个 `DROP COLUMN` 迁移 | 迁移检查红(C9) |
| N7 | 在业务类上直接用 `@ConditionalOnProperty` | ArchUnit 红(C10) |
| N8 | 异步任务未传递 MDC | 测试红(C12) |

**这 8 个用例如能全部通过,才算真正达到"防劣化"**——它们证明的是"体系能拦住退化",而不是"体系存在"。

### 5.3 防劣化的自指闭环

**v1.0 的漏洞:守护者自身无保护。** 防线 2 用测试守护资源登记,但当时无测试基类、CI 跳过测试——**守护者脚下是空的**。

`[目标]` 闭环规则:

1. **所有拦截机制自身必须有测试**(ArchUnit 规则有测试、`ServerModeConsistencyCheck` 有测试、`TraceIdFilter` 有测试);
2. **门禁必须在 CI 强制**,禁止 `-DskipTests` 进入 CI 流水线(§2.2);
3. **元规则**:新增任何架构约束时,必须同时提交"该约束的负向用例",否则视为未完成(§5.2)。

> 这三条共同保证:**防劣化体系不会自己劣化。**

## 7. 明确不做的事(边界声明)

以下均为**经过考虑的否定**,不是遗漏。每条都对应一个"为什么不做"的论证(建议按 §3.2 正式化为 ADR)。

| 不做 | 理由 |
|---|---|
| **分布式部署 / 集群** | 单实例 + 外置库足以支撑"公司内网自用工具平台"。引入分布式会带来会话共享、一致性、部署复杂度,与"轻量工具"定位冲突。**代价必须显式声明**:见下方"单实例的残留风险" |
| **微服务拆分** | 仍是**单进程多模块**。模块化解决开发期边界与可替换性,不是部署隔离。拆微服务会让"一个平台装多个工具"变成运维负担 |
| **运行时热插拔 jar** | 工具在**构建期**接入。运行时装卸 jar 需要类加载器隔离与版本兼容治理,收益远小于成本 |
| **多租户(B2B SaaS 式)** | 只做"多用户共享一个实例",不做"多组织数据强隔离"。后者需要全表租户维度改造,非目标场景 |
| **`AbstractRoutingDataSource`** | `架构文档` §0.1 已论证:DevNest 是"多数据源并存、按 ID 取用",池工厂才是对的抽象 |
| **统一的资源释放编排** | §4.2 已论证:登记 ≠ 接管。释放仍自治,避免引入顺序与失败传播问题 |
| **URL 版本化(`/v1/`)** | §3.3 已论证:无独立发布周期的第三方消费者,改用字段级兼容策略 |
| **trace 后端(Jaeger/Zipkin/Collector)** | §4.3.1 已论证:保留 traceId+spanId 与结构化日志,不引入额外部署组件 |
| **全局限流(网关式)** | §4.5 已论证:改用工具级/资源级隔离(bulkhead),更贴合"多工具互不干扰"的目标 |

### 单实例的残留风险(必须显式声明)

**`不做集群` 可以接受,但"单实例"带来的语义必须写死,否则会变成空洞:**

| 风险 | 目标设计 |
|---|---|
| **重启即丢运行时状态** | 明确声明:隧道/控制台会话/业务池为 **`ephemeral`(可丢弃)**;重启后由 `TunnelBootstrapRunner` 按 `last_running` **重建**隧道(✅ 已有),控制台会话不重建(前端需重连)。**这是有意选择,不是遗漏。** |
| **无接管节点** | 单实例天然无 HA。缓解:优雅关闭链路(✅)+ 资源快照报告,保证"干净停机",而非"崩溃丢失" |
| **端口是稀缺资源** | `PortAllocator` 需修复 TOCTOU 竞态(能力清单 §5 第 1 项),否则并发建隧道会双分配同一端口 |

## 10. 落地路线(批次与依赖)

> **执行级计划见 [20260910_目标架构落地路线图.md](20260910_目标架构落地路线图.md)** —— 本节只给批次概要,任务清单、落点、阶段门禁、风险与规模以该文档为准。

**严格按成熟度级别推进:跨越 L2 直接做 L3/L4 是无效的**——L4 的自动拦截依赖 L2 的测试与门禁作为执行载体。

### 批 0 · 地基(L1 → L2)—— 先于一切花哨设计

> 判据:没有这一批,v1.0 与 v2.0 的所有"自检"都不可信。

1. CI 去掉 `-DskipTests`,改 `mvn verify`;
2. JaCoCo 接入 + **增量覆盖率**阈值(G2);
3. enforcer 增加 `dependencyConvergence`(C2);
4. OWASP `dependency-check` 接入(G3/C3);
5. **测试基座**:`ResourceRegistryTestBase` + Testcontainers(MySQL 8 / Redis)(§2.3);
6. **ArchUnit 骨架** + 首批规则 C4/C10/C13。

### 批 1 · 形态与装配(S2 前置项)

7. 形态元注解 + `devnest.mode`(§4.1),`matchIfMissing=true` 默认 LOCAL;
8. 形态与 profile 正交化,`application-desktop.yml` 退役(§4.1.1);
9. 三个 SPI 补 `@ConditionalOnMissingBean` 装配契约;
10. `ServerModeConsistencyCheck` 防退化自检(C6);
11. **负向用例 N1/N3/N7**(§5.2)。

### 批 2 · 可治理

12. `ResourceRegistry` + 9 类资源登记 + 启动自检(§4.2);

### 批 3 · 安全与隔离(管得住)

16. 鉴权锚点按形态装配(§4.1.2/N3);
