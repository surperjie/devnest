## 0. 与 v1.0 初始设计的关系

v1.0《项目架构》描述的是**设计意图**,本文档描述的是**实现现状**。实现过程对设计稿做了 12 处调整。判断这些调整的性质只有一条标准:**被砍掉的能力,替代方案是否真的提供了等价能力?** 提供 → 取舍(2 处);没提供 → 能力缺失(5 处);另 5 处是中性变化。此外还有 2 处**反向差异**——设计稿漏了、实现时补上的。详见 §0.1–§0.5。**有冲突时以本文档为准。**

### 0.1 取舍:替代方案确实等价或更优(2 处)

共同特征是"Spring 接管了原设计的职责",回退反而更差。

| 主题 | v1.0 设计 | 实际实现 | 为什么算等价 |
|---|---|---|---|
| 优雅关闭 | `ShutdownHook` 六步编排 | Spring 生命周期 + `server.shutdown=graceful` | Spring 的销毁链本身就是"逆序 + 逐个容错"(单个 `@PreDestroy` 抛异常只记 warn 日志,不中断其他 Bean),框架提供了比手写更可靠的等价能力,见 §4.4 |
| 动态数据源 | `DynamicDataSourceManager` / `AbstractRoutingDataSource` | `core/pool/HikariPoolFactory`(池工厂,非路由) | `AbstractRoutingDataSource` 解决的是"同一逻辑库名路由到不同物理库"(读写分离/多租户);DevNest 是"多数据源并存、按 ID 取用",池工厂才是对的抽象,路由能力非所需,见 §4.6 |

### 0.2 能力缺失:替代方案不等价(5 处)

这一组是**复核后的修正结论**。早先版本把"扩展机制""资源释放"也归入 §0.1 的取舍,理由是"改用框架原生能力"——这个理由站不住:Spring 并未接管这两项职责。区别在于,它们不是"换一种方式做同一件事",而是"这件事没人做了"。

#### 0.2.1 架构治理层(2 处)

| 主题 | v1.0 设计 | 实际实现 | 丢失了什么 |
|---|---|---|---|
| 扩展机制 | `ToolModule` SPI + `ToolModuleRegistry` | 无此机制 | 模块注册、生命周期启停、元信息的统一治理层,见 §2.4 |
| 资源释放 | `ResourceRegistry` 统一注册、逆序释放 | 5 处散落的 `@PreDestroy` | 全局视图、释放顺序、异常兜底、资源清单,见 §4.3 |

**`core/spi` 不是 `ToolModule` 的替代品**。`core/spi` 的两个接口(`TunnelPortForwarder`、`BastionLookupService`)解决的是**依赖倒置**——让 console/datasource/redis 复用隧道能力而不直接依赖 `devnest-tunnel`。它不承担模块注册职责,二者用途不同。`ToolModule` 是**未建设**,不是"被替代"。

另需澄清一个常见归因:`ToolModuleRegistry` 管的是**模块注册与生命周期**,不是 HTTP/WS 安全拦截。把"安全校验散落各模块"记到它头上并不成立——v1.0 从未设计过统一安全切面。

**`ResourceRegistry` 的缺失曾被现实验证**:`RedisPoolFactory.shutdown()` 存在却没有 `@PreDestroy`,应用关闭时永远不会被调用(已于本次修复,见 §10.4)。这正是"统一登记表消失"的直接后果——没有清单可对照,漏挂一个回调,编译器不报错、测试测不出、代码审查也无参照物。

#### 0.2.2 功能承诺(3 处)

| 主题 | v1.0 设计 | 实际实现 | 缺口 |
|---|---|---|---|
| SQL 防护 | 白名单,仅放行 SELECT/SHOW/DESCRIBE/EXPLAIN,"根本性杜绝 DDL" | **黑名单**,只拦文件读写/盲注/动态执行,**DML 与 DDL 放行** | 安全边界收缩,见 §7.5 |
| 前端编辑器 | Monaco Editor | CodeMirror 6 | 体积小很多,但 SQL 智能补全与语法诊断明显弱于 Monaco |
| 容错组件 | Resilience4j | 手写重连 | 能工作,但缺熔断、退避策略、指标导出 |

建议逐项评估是否补回。

### 0.3 中性:等价替换或范围调整(5 处)

| 主题 | v1.0 设计 | 实际实现 | 说明 |
|---|---|---|---|
| 模块划分 | 单工程 `com.devnest.module.*` 包 | 8 个独立 Maven 模块 | **升级**:物理隔离 + 编译期强制边界,见 §0.5 |
| Redis 客户端 | Lettuce + commons-pool2 | Jedis 4.4.6 + `JedisPool` | 能力相当;根因是 Spring Boot BOM 未锁 Jedis 版本,属被动选择 |
| 服务端口 | 8080 | 38080 | 避开常用端口 |
| 配置库落盘 | `~/devnest/devnest.mv.db` | `./data/`(开发)或 `%LOCALAPPDATA%\DevNest\data\`(安装版) | 见 §6.3 |
| 模块清单 | 含 `http` / `ai` | 无 `http` / `ai`,多出 `pipeline` | 范围重排,非缩水 |

### 0.4 反向差异:设计稿缺失、实现时补上的(2 处,不计入上述 12 处)

对比时不能只数"哪些没实现",还要看"哪些是设计漏了后来补的"。这类"实现比设计更严谨"之处,恰恰是设计评审最该抓的。

| 主题 | v1.0 设计 | 实际实现 | 说明 |
|---|---|---|---|
| Actuator 暴露面 | **完全未提** | 端点按来源 IP 分级,`show-details` 由 `always` 收紧为 `when-authorized` | 照 v1.0 做,任何能访问端口者都能读到完整连接池信息并调用 shutdown,见 §7.3 |
| WebSocket 鉴权 | **完全未提** | 一次性 TOFU token(32B 随机、TTL 30s、用后即焚) | 实现时才发现"知道 consoleId 就能直连 WS"这一漏洞,见 §5.2 |

### 0.5 模块边界:从"约定"加固为"编译期强制"(本次变更)

v1.0 §2 只写了规则——"禁止反向依赖、禁止跨模块横向依赖(除非经 core 抽象)",并**未要求编译期强制**。初版实现拆出 8 个 Maven 模块后,物理隔离是有了,但边界仍靠人工评审:非法的横向依赖只要在 pom 里多写一行,编译、测试、构建全部通过。

**Maven 原本只提供两条强制力**:引用未声明的模块会编译失败;形成循环依赖会让 reactor 构建失败。这两条都拦不住"新声明一条不该有的依赖"。

现已用 `maven-enforcer-plugin` 闭合:

| 模块 | 规则 |
|---|---|
| `devnest-common` | 禁止依赖任何内部模块(`com.devnest:*`) |
| `devnest-core` | 只允许依赖 common,禁止反向依赖业务模块与 boot |
| `devnest-tunnel` / `devnest-console` / `devnest-datasource` / `devnest-redis` / `devnest-pipeline` | 禁止横向依赖其余 4 个业务模块,禁止依赖 boot |
| `devnest-boot` | 不设限(唯一聚合点) |

规则绑定 `validate` 阶段,违规直接构建失败。实测把 `devnest-console` 加进 `devnest-redis`:

```
Rule 0: org.apache.maven.enforcer.rules.dependency.BannedDependencies failed with message:
com.devnest:devnest-redis:jar:1.0.0
   com.devnest:devnest-console:jar:1.0.0 <--- banned via the exclude/include list
```

各模块 pom 的 `<build>` 段即为该模块的架构契约;新增合法依赖需同步调整规则,这正是"边界规则就近声明"的好处。

> 需要区分:此机制约束的是 **pom 里声明的依赖**,不是代码里的引用。跨模块引用未声明的类本来就编译不过,两者叠加后,"偷偷引用内部实现类"在编译期已无可行路径。

## 1. 系统总览

DevNest 是**纯本机单机工具**:后端常驻 `127.0.0.1:38080`,由桌面壳拉起、随桌面壳退出,全链路不经过公网。

```
┌──────────────────────────────────────────────────────────────┐
│  桌面壳:Tauri 2(Rust) + Vue 3                               │
│  ─ 纯 UI,无业务逻辑                                          │
│  ─ 负责:拉起/关闭后端、单实例锁、窗口                              │
│                          │ HTTP + WebSocket                    │
│                          │ 127.0.0.1:38080(仅回环)            │
└──────────────────────────┼───────────────────────────────────┘
                           │
┌──────────────────────────┼───────────────────────────────────┐
│  Spring Boot 3 内核(Java 21,虚拟线程)                       │
│                                                               │
│  ┌──────────────────────────────────────────────────────┐    │
│  │ 业务模块(互不依赖,均只依赖 core)                     │    │
│  │  tunnel   console   datasource   redis   pipeline     │    │
│  └──────────────────────┬───────────────────────────────┘    │
│                         │                                     │
│  ┌──────────────────────┴───────────────────────────────┐    │
│  │ core   领域基础:BaseEntity / 线程池 / 连接池工厂 /      │    │
│  │        缓存 / HTTP / 日志脱敏 / SPI 接口               │    │
│  ├──────────────────────────────────────────────────────┤    │
│  │ common 通用设施:加密 / 异常码 / 响应体 / CORS /         │    │
│  │        Actuator 安全 / SQL 校验                        │    │
│  └──────────────────────────────────────────────────────┘    │
└───────────┬───────────────────────────────┬──────────────────┘
            │                               │
   ┌────────┴─────────┐          ┌──────────┴──────────────┐
   │ 配置库(DevNest 自身)│          │ 用户业务资源(经 SSH 隧道) │
   │ H2(dev/desktop)   │          │ MySQL / 达梦 / Redis     │
   │ MySQL(prod)       │          │ 动态池,按需建/销         │
   └──────────────────┘          └─────────────────────────┘
```

**三条不变量**(贯穿全部设计):

1. **仅回环**:`server.address=127.0.0.1`,无多用户、无鉴权体系,安全边界靠"绑卡 + CORS 白名单 + WS 一次性 token"三层。
2. **依赖单向**:业务模块之间零依赖,横向协作一律经 `core/spi` 接口。
3. **配置库与业务资源物理隔离**:两套完全独立的连接池,事务不串。

## 2. 模块拓扑

### 2.1 依赖关系

8 个 Maven 模块,`devnest-parent` 聚合。依赖方向严格单向,无循环:

```
devnest-boot ─┬─> devnest-tunnel ─────┐
              ├─> devnest-console ────┤
              ├─> devnest-datasource ─┼─> devnest-core ─> devnest-common
              ├─> devnest-redis ──────┤
              └─> devnest-pipeline ───┘
```

**铁律**:

- 业务模块**只允许**依赖 `core`(进而传递依赖 `common`);
- 业务模块之间**禁止**互相 `<dependency>`,需要协作时在 `core/spi` 定义接口,由提供方实现(见 §4.1);
- `devnest-boot` 是唯一可执行模块,唯一使用 `spring-boot-maven-plugin` 的模块;
- 版本号只在根 POM 声明,子模块一律不写 `<version>`。

### 2.2 模块职责

| 模块 | 职责 | 关键依赖 |
|---|---|---|
| `devnest-common` | 通用设施:加密、异常/错误码、统一响应、CORS、Actuator 安全、SQL 校验、当前用户 | web、security、actuator、validation、bouncycastle |
| `devnest-core` | 领域基础:`BaseEntity`、统一虚拟线程池、连接池工厂、缓存、OkHttp、日志脱敏、SPI 接口 | jpa、jdbc、cache、caffeine、okhttp、micrometer、blackbird |
| `devnest-tunnel` | SSH 隧道:跳板管理、端口转发、心跳重连、端口分配、启动继承 | jsch、mapstruct |
| `devnest-console` | 远程控制台:会话配置、WebSocket 终端、一次性 token 握手 | websocket、jsch、mapstruct |
| `devnest-datasource` | 数据源:MySQL/达梦连接、库表树、分页预览、SQL 执行与历史 | mapstruct、mysql-connector-j |
| `devnest-redis` | Redis:实例管理、键空间浏览、命令白名单执行 | jedis、jpa、validation |
| `devnest-pipeline` | 流水线:多步骤脚本编排、本机进程执行、跨步骤变量传递 | mapstruct |
| `devnest-boot` | 启动:聚合业务模块、Flyway 迁移、profile 配置、fat jar | flyway、h2、mysql、actuator |

### 2.3 为什么没有 `ToolModule` SPI

v1.0 设计的 `ToolModule`(要求每个模块实现 `name/onStart/onShutdown/isEnabled` 空壳)+ `ToolModuleRegistry` 统一编排,实现时被放弃了,原因:

- **收益为负**:Spring 本身就是模块容器,`@Component` + `@PreDestroy` 已能完成生命周期管理;再套一层 SPI 只是把 Spring 已有能力包装一遍。
- **"扩展点"是假需求**:新增模块(Kafka/ES)本来就要写 pom、加依赖、写 Controller,不会因为多了个接口就"不动其他代码"。
- **实际需要的是依赖倒置,不是扩展注册**:真正的问题是 `console`/`datasource`/`redis` 想用隧道能力却不想依赖 `tunnel` 模块。这个问题用**按需的小接口**解决,而不是**全局的大 SPI**。见下节。

### 2.4 实际的扩展机制:`core/spi`

`core` 定义两个接口,`tunnel` 提供实现。业务模块依赖接口,不感知实现细节:

| 接口 | 位置 | 实现 | 消费者 |
|---|---|---|---|
| `TunnelPortForwarder` | `core/spi` | `tunnel/spi/TunnelPortForwarderImpl` | console、datasource、redis |
| `BastionLookupService` | `core/spi` | `tunnel/spi/BastionLookupServiceImpl` | console、datasource、redis(导入导出) |

```java
// core/spi/TunnelPortForwarder.java —— 业务侧完全不知道 SshTunnelManager/PortAllocator 的存在
public interface TunnelPortForwarder {
    int allocateTunnel(Long bastionId, String remoteHost, int remotePort);
    void releaseTunnel(int allocatedLocalPort);
    boolean isBastionRunning(Long bastionId);
}
```

这带来两个实际好处:

- **编译期防环**:`console` 的 pom 里没有 `devnest-tunnel`,物理上不可能误用其内部类;
- **可测试**:业务模块单测 mock 接口即可,不需要起 SSH。

**新增模块的正确姿势**:如果新模块需要隧道能力 → 直接用 `TunnelPortForwarder`;如果需要新的跨模块协作 → 在 `core/spi` 加**一个小接口**,由提供方实现。不要造通用 SPI 框架。

## 3. 分层与包结构

### 3.1 模块内统一分层

每个业务模块内部保持一致的目录语义:

```
devnest-<module>/src/main/java/com/devnest/<module>/
├── api/           # Controller(薄,只做参数接收与响应包装)
├── service/       # 服务接口
│   └── impl/      # 服务实现(事务边界在这一层)
├── repository/    # Spring Data JPA Repository
├── entity/        # JPA 实体(继承 core 的 BaseEntity)
├── dto/           # 请求/响应对象
└── mapper/        # MapStruct 接口(编译期生成 Impl)
```

部分模块按需追加专属包:

| 模块 | 专属包 | 含义 |
|---|---|---|
| tunnel | `tunnel/`、`port/`、`model/`、`bootstrap/`、`config/`、`spi/` | 隧道实例、端口分配器、状态机、启动继承、配置、SPI 实现 |
| console | `session/`、`ws/` | 运行时会话、WebSocket 与 token |
| redis | `pool/`、`security/` | Jedis 池工厂、命令白名单 |
| pipeline | `run/`、`exec/`、`util/`、`constant/` | 运行编排、进程执行、模板渲染、常量 |

### 3.2 依赖方向

```
api  →  service  →  repository  →  entity
          ↓
        mapper / dto
```

- Controller **不允许**直接注入 Repository 或返回 Entity;
- 事务注解(`@Transactional`)只出现在 `service/impl`;
- 实体字段加密/解密由实体自身方法 + `CryptoService` 完成(如 `SshBastion.decryptPassword(crypto)`)。

### 3.3 包命名的一个例外

`core` 与 `common` 不按上述分层组织,它们是**基础设施库**,按能力分包:

```
com.devnest.common
├── config/       ActuatorSecurityConfig, CorsConfig
├── context/      CurrentUserProvider, LocalUserProvider
├── crypto/       CryptoService, KeyManager
├── exception/    BizException, ErrorCode, GlobalExceptionHandler
├── response/     ApiResult
└── sql/          SqlSanitizer

com.devnest.core
├── cache/        CacheClusterConfig
├── config/       CryptoConfig
├── http/         OkHttpConfig
├── json/         JacksonConfig
├── log/          SensitiveDataLogFilter
├── persistence/  PersistencePoolConfig, entity/BaseEntity
├── pool/         HikariPoolFactory, PoolProperties
├── spi/          TunnelPortForwarder, BastionLookupService
└── thread/       VirtualThreadExecutorConfig
```

## 4. 核心机制

### 4.1 SPI 依赖倒置

见 §2.4。核心是:**跨模块能力经 `core/spi` 暴露接口,实现留在提供方模块,消费方只依赖接口**。

### 4.2 统一虚拟线程执行器

`core/thread/VirtualThreadExecutorConfig` 暴露**唯一**的虚拟线程池 Bean:

```java
@Bean(name = "virtualExecutorService", destroyMethod = "shutdown")
public ExecutorService virtualExecutorService() {
    return Executors.newVirtualThreadPerTaskExecutor();
}
```

**约定**:全项目所有异步 IO 都必须经此 Bean 提交,**禁止**散写 `Executors.newVirtualThreadPerTaskExecutor()` 或 `Thread.startVirtualThread()`。

现状消费者:

| 消费者 | 用途 |
|---|---|
| `SshTunnelManager` / `SshTunnelInstance` | 隧道连接、心跳、重连 |
| `TunnelBootstrapRunner` | 启动时并发恢复隧道 |
| `ConsoleSessionManager` | 终端读写循环 |
| `PipelineRunManager` | 流水线运行(经 `@Qualifier("virtualExecutorService")` 注入) |

关闭时由 `virtualExecutorCleanup`(`DisposableBean`)等待最多 3s,超时 `shutdownNow()` 并记录丢弃任务数。

> 注意:`spring.threads.virtual.enabled=true` 让 Tomcat 请求线程、`@Async`、调度任务也虚拟线程化;上述 Bean 是**业务侧显式提交异步任务**的统一出口。两者互补。

### 4.3 资源生命周期:各模块自治

**没有** `ResourceRegistry`。每个持有运行时资源的模块自己管理自己的资源,并挂 `@PreDestroy`。

| 资源 | 持有者 | 释放方式 |
|---|---|---|
| 配置库连接池 | `core/persistence/PersistencePoolConfig` 的 `@Primary HikariDataSource` Bean | Spring 销毁 Bean 时推断调用 `close()` |
| 业务数据源池 | `core/pool/HikariPoolFactory` | `@PreDestroy onShutdown()` → `destroyAll()` |
| SSH 隧道 | `tunnel/tunnel/SshTunnelManager` | `@PreDestroy stopAll()` |
| 控制台会话 | `console/session/ConsoleSessionManager` | `@PreDestroy closeAll()` |
| 流水线运行 | `pipeline/run/PipelineRunManager` | `@PreDestroy shutdown()` → 逐个 `cancel()` |
| WS token 清理线程 | `console/ws/WsTokenManager` | `@PreDestroy stopCleaner()` |
| 虚拟线程池 | `core/thread/VirtualThreadExecutorConfig` | `destroyMethod="shutdown"` + `DisposableBean` |
| Redis 连接池 | `redis/pool/RedisPoolFactory` | `@PreDestroy shutdown()`(曾漏挂,已修复,见 §10.4) |

**这个取舍是对的**:统一注册表在资源类型多样(池/线程/会话/子进程)时,反而要处理"谁先关、关失败怎么办",而各模块自治时每个 `@PreDestroy` 只需关心自己的资源,失败也只影响自己。

### 4.4 优雅关闭链路

```
用户关闭窗口
   │
   ▼
Tauri(Rust):POST /actuator/shutdown,等待上限 SHUTDOWN_WAIT_SECS = 10s
   │
   ▼
Spring Boot:
   1. server.shutdown=graceful —— 停止接收新请求,等在途请求结束
      (上限 spring.lifecycle.timeout-per-shutdown-phase = 10s)
   2. 销毁 Bean 上下文 → 各 @PreDestroy / DisposableBean 回调
   3. 关闭配置库连接池
   │
   ▼
Tauri:若 10s 内未退出 → 强杀进程
```

两侧超时都是 10s,是刻意对齐的:后端先自己收尾,强杀只作为兜底。

各 `@PreDestroy` 的执行顺序由 Spring 按 Bean 依赖关系逆序决定,**不保证**业务语义上的先后。但由于资源之间无强耦合(隧道与控制台会话各自独立),任意顺序都安全。

### 4.5 加密与密钥管理

```
KeyManager  ──生成/加载──>  主密钥(32B)
    │                          │
    │                          ├─ 落盘:%USERPROFILE%\.devnest\master.key
    │                          │
    └──> CryptoService <───────┘
             │
             └─ AES-256-GCM,密文 = base64( IV(12B) || ciphertext || tag(16B) )
```

- `CryptoService` 在 `common/crypto`,由 `core/config/CryptoConfig` 注册为 Bean;
- 加密字段入库:`SshBastion.passwordCipher`、`RemoteConsole.passwordCipher`、`DataSourceConfig.passwordCipher`、`RedisInstanceConfig.passwordCipher`;
- 响应体一律脱敏为 `********`(`CryptoService.MASK`);
- `CryptoService.isPlaceholder()` 用于导入场景:导出文件里的密码是脱敏占位符,导入时**不得**当作真实密码入库(启动隧道时会显式报错提示重新输入)。

### 4.6 连接池:两套池,物理隔离

| | 配置库池 | 业务数据源池 |
|---|---|---|
| 数量 | 1 个(`@Primary`) | N 个,按 `datasourceId` 懒创建 |
| 管理 | Spring Boot | `HikariPoolFactory` |
| 参数 | `PersistencePoolConfig` 显式声明 + `spring.datasource.hikari.*` 覆盖 | `PoolProperties`(`devnest.pool.*`) |
| 上限 | 固定 | `max-pools` 闸门(默认 20) |

`HikariPoolFactory` 的关键设计:

- **总量闸门**:`getOrCreate` 先判 `poolCount >= maxPools` 再建池,避免"建好才发现超限"造成瞬时连接浪费;
- **探测不占名额**:`probe()` 用临时池(max=1)做连通性测试,不入 `poolMap`;
- **泄漏检测兜底**:`leak-detection-ms` 低于 Hikari 硬性下限 2000ms 时按 2000 处理并告警,避免一个笔误让数据源不可用;
- **不负责失效时机**:只提供"建"与"销毁",配置变更后由上层调用 `destroyPool` 丢弃旧池(见 §5.3)。

理论最大连接数 ≈ `max-pools × max-pool-size` = 20 × 8 = 160;活跃池数量以 `devnest.pool.active.count` 指标暴露到 Actuator。

### 4.7 缓存

`core/cache/CacheClusterConfig` 声明了 `@EnableCaching` 与三个 Caffeine 缓存:

| Bean | 规格 | 预期用途 |
|---|---|---|
| `cacheManager`(默认) | 500 条 / 写后 5min | 通用热数据 |
| `datasourceSchemaCache` | 200 条 / 访问后 1h | 库表元数据 |
| `aiRateLimitCache` | 10000 条 / 写后 1min | AI 调用限流 |

> ⚠️ 当前**没有任何业务代码使用**这些缓存(无 `@Cacheable`/`@CacheEvict`,三个 Cache Bean 也无人注入)。属预留设施,见 §10。

## 5. 业务模块

### 5.1 tunnel —— SSH 隧道底座

隧道是全部内网能力的底座:数据库、Redis、控制台都靠它穿透。

**核心模型**

```
SshBastion(跳板机) 1 ──── n SshPortMapping(端口映射)
       │
       └─ 运行时:1 个 SshTunnelInstance
```

| 类 | 职责 |
|---|---|
| `SshTunnelInstance` | 一跳板一实例。持有 JSch `Session` + 心跳调度 + 状态机 + 重连任务句柄 |
| `SshTunnelManager` | Spring Bean,`Map<Long, SshTunnelInstance>`,统一启停/查询/关闭 |
| `PortAllocator` | 本机空闲端口分配 |
| `TunnelState` | 状态机枚举 |
| `TunnelBootstrapRunner` | 启动继承 |

**状态机**

```
IDLE → CONNECTING → RUNNING → RECONNECTING → RUNNING
                       │            │
                       └────────────┴──> ERROR → CLOSED
                                          ↑
                                    手动停止/程序退出
```

`TunnelState.isTerminal()` = `CLOSED || ERROR`。**终态实例允许被重新拉起**,非终态视为"已在运行"并拒绝重复启动。

**异步启动 + 进度外显**:`start()` 立即返回,连接与每次重试的进展通过 `LifecycleListener` 回调写入 `statusDetail`,前端轮询即可看到"正在第几次重试"。

**启动继承**:`TunnelBootstrapRunner` 监听 `ApplicationReadyEvent`,查询 `ssh_port_mapping.last_running = true` 的跳板并发恢复。设计要点:

- 恢复失败**只告警不阻断启动**;
- 用虚拟线程池并发恢复,最后起一个 2s 延时任务打印"成功 N / 失败 M"汇总(非强制,不阻塞端口监听);
- 库未初始化/迁移未执行时静默跳过。

**`last_running` 的写时机**(容易踩坑,代码里有显式注释):

| 场景 | 是否更新 `last_running` |
|---|---|
| 用户主动停止 | 是 → `false` |
| 隧道进入 RUNNING / ERROR / CLOSED | 是 → `true` / `false` |
| **程序退出(`stopAll`)** | **否** —— 保持用户上次的意图,下次启动才能继承恢复 |

### 5.2 console —— 远程控制台

**连接双模式**

| 模式 | 判定 | 连接目标 |
|---|---|---|
| 直连 | `bastionId == null` | 直接连 `remoteHost:remotePort` |
| 隧道 | `bastionId != null` | 经 `TunnelPortForwarder` 分配本地端口,再连 `127.0.0.1:allocatedPort` |

**运行时结构**

```
WebSocket 会话(wsSessionId) 1 ──── 1 ConsoleSession
                                        ├─ JSch ChannelShell(PTY, xterm, 80x24 起)
                                        ├─ 分配的隧道端口(直连模式为 null)
                                        └─ 虚拟线程读循环 → onOutput 回调推前端
```

`ConsoleSessionManager` 负责开/写/改窗口尺寸/关,`@PreDestroy closeAll()` 兜底。

**WebSocket 一次性 token(TOFU)**

这是本项目安全设计里最值得说的一处。历史缺陷是:**任何人只要知道 `consoleId` 就能直接建 WebSocket 连接**,绕过所有 HTTP 校验。修复方案:

```
1. 前端 POST /api/console/{id}/ws-token   → 后端生成 32B 随机 token,绑定 consoleId,TTL=30s
2. 前端 ws://.../ws/console/{consoleId}?token=xxx
3. ConsoleHandshakeInterceptor:
     解析路径 consoleId → verifyAndConsume(token, consoleId)
     校验:存在 && 未过期 && consoleId 匹配 → 通过后立即从 Map 删除(一次性)
4. 失败:HTTP 401 + WARN 日志(含脱敏 token、客户端 IP)
```

实现细节:

- `WsTokenManager` 是**单例 Bean,状态为实例字段**,不是静态字段;清理调度器随 Bean 生命周期创建/销毁 —— 这样便于测试隔离,也能随容器优雅关闭;
- 清理任务每 10s 扫一次过期 token,防 Map 无限增长;单次清理异常被捕获,**不能中断调度器**;
- 日志里的 token 只保留前后 3 位(`maskToken`);
- `WsTokenManager` 上**没有**测试,见 §10。

### 5.3 datasource —— 数据源与 SQL

**支持类型**:MySQL(`com.mysql.cj.jdbc.Driver`)、达梦 DM8(`dm.jdbc.driver.DmDriver`)。达梦驱动不在 Maven 中央仓库,见 §9.3。

**连接池复用与失效**(`DataSourceServiceImpl` 的核心逻辑):

```
poolKey = "ds:" + datasourceId
```

配置变更时,不是无脑重建池,而是比较**连接指纹**:

```java
connectionFingerprint = dbType | host | port | databaseName | username | passwordCipher | tunnelBastionId
```

- 指纹**变了**(改了 host/端口/库名/账号/密码/隧道)→ 旧池已指向错误目标 → `databaseQueryService.evict(id)` 丢弃,下次查询按新配置重建;
- 指纹**没变**(只改名称/备注)→ **不重建**,避免平白打断正在执行的查询。

这个"指纹判断"有专门单测守护(`DatabaseQueryServiceImplEvictTest`、`DataSourceServiceImplTest`)。

**端口与池同生共死**:隧道端口和连接池必须在同一时机回收,因此 `destroyPool` 不做延迟,由调用方决定何时丢弃(代码注释明确写了这一点)。

**SQL 执行**:`DatabaseQueryServiceImpl`(31.7KB,见 §10)负责库表树、分页预览、多语句执行、执行日志、结果集上限控制。

### 5.4 redis —— Redis 可视化

**客户端**:Jedis 4.4.6 + `JedisPool`(非 Lettuce)。根 POM 注释说明原因:Spring Boot BOM 未锁 Jedis 版本,自行管理。

**池管理**(`RedisPoolFactory`):

- `poolKey = "redis:" + instanceId`;
- 双 Map 结构:`pools`(池)+ `tunnelPorts`(池对应的隧道端口),**销毁池时同步释放隧道端口** —— 避免"只关池漏掉端口";
- `borrow()` 探测失败时销毁旧池并重建一次,仍失败才抛 `REDIS_CONNECT_FAILED`;
- `probe()` 用临时连接,隧道模式下建临时转发,`finally` 释放;
- `rebuildPool()` 只在连接目标/池参数变化时由上层调用,改名改备注不打断正在执行的命令(与 datasource 同一设计哲学)。

**命令白名单**(`RedisCommandWhitelist`):**Fail-Closed** —— 显式枚举允许的命令,未知命令一律拒绝。

- 只读命令集(`GET`/`SCAN`/`HGETALL`/`ZRANGE`/`XINFO`/`INFO`/`EVAL_RO` ...)
- 写命令集(独立 `WRITE_COMMANDS`)
- 直接拒绝:`BGSAVE`/`FLUSHALL`/`FLUSHDB`/`KEYS`/`SHUTDOWN`/`CONFIG`/`DEBUG`/`OBJECT`/`REPLCONF`/`MIGRATE`/`SWAPDB`

拒绝 `KEYS` 是刻意的 —— 强制走 `SCAN`,避免阻塞 Redis。

### 5.5 pipeline —— 流水线

> 该模块在 `需求.md` 与 README 的模块清单中**均未出现**,属后续追加能力。

**定位**:本机多步骤脚本编排。把"一连串要按顺序跑的本地命令"存成可复用的流水线,支持跨步骤传值、并发控制、停止。

**数据模型**(4 张表)

```
pipeline_definition(定义) 1 ── n pipeline_step(步骤)
        │
        └─ 1 ── n pipeline_run(运行实例) 1 ── n pipeline_step_run(步骤运行记录)
```

**步骤类型**:`batch` / `cmdline` / `powershell` / `python`

**运行状态**:`WAITING` / `RUNNING` / `SUCCESS` / `FAILED` / `STOPPED`
**步骤状态**:`RUNNING` / `SUCCESS` / `FAILED` / `SKIPPED`
**失败策略**:`abort`(中断)/ `continue`(继续)
**输出解析**:`none` / `keyvalue`(把 stdout 按 k=v 解析进跨步骤上下文)

**并发模型**(`PipelineRunManager`)—— 两层约束:

| 层级 | 约束 | 手段 |
|---|---|---|
| 单条流水线 | 同时只允许 1 个活动运行 | 服务层 DB 行锁为准 + 内存 `Set<Long> runningPipelineIds` 二次拦截 |
| 全局 | 不同流水线并行,总数受限 | `Semaphore(max-concurrent-runs)`,默认 5 |

**执行链路**

```
PipelineRunManager.submit(runId, pipelineId)
   │  登记 handle + 标记 pipeline 占用
   ▼
虚拟线程池执行
   │  permits.acquire()  ← 全局并发闸门
   ▼
PipelineExecutionEngine.execute(runId, handle)
   │  按序执行步骤 → LocalProcessExecutor 起子进程
   │  收集 stdout/stderr → 解析 → 写入跨步骤上下文
   ▼
finally:释放 permit、清理 handle、解除 pipeline 占用
```

**进程执行**(`LocalProcessExecutor`):

- 子进程输出字符集默认 `auto`:Windows 用 GB18030,其余平台 UTF-8(可显式指定);
- 工作区:`workspace-dir`(默认 `data/pipeline`),每个 run 建独立子目录;
- stdout 进上下文的**字节上限 200,000**(`CTX_STDOUT_CAP`),防内存爆掉;
- `ProcessKiller` 负责停止时终止进程树(Windows 下子进程常派生子进程,只杀父进程会留孤儿);
- `TemplateRenderer` 做步骤间变量替换;`PipelineJson` 处理 JSON 序列化。

**优雅关闭**:`PipelineRunManager.@PreDestroy shutdown()` 遍历所有 `RunningHandle.cancel()`,终止运行中的子进程 —— 不留孤儿进程。

## 7. 安全设计

因为不做多用户与鉴权,安全靠**边界收敛 + 分层兜底**,而非身份体系。

### 7.1 网络边界

- `server.address: 127.0.0.1` —— 只绑回环,局域网/外网不可达(可用 `DEVNEST_SERVER_ADDRESS` 覆盖);
- 桌面壳运行时把后端工作目录固定为 `%LOCALAPPDATA%\DevNest`,相对路径不会因启动位置漂移。

### 7.2 CORS:双层防护

1. **`CorsConfig` 白名单**:`allowedOriginPatterns` 精确匹配 `127.0.0.1:1420` / `localhost:1420` / `tauri://localhost` / `http://tauri.localhost`(可由 `devnest.cors.allowed-origins` 覆盖);
2. **兜底 Filter**:任何带 `Origin` 头且不在白名单的请求,直接 `403` + `code=4030 CORS_ORIGIN_BLOCKED`。

第 2 层是刻意加的 —— 不依赖 `CorsRegistry` 是否覆盖到具体路径,防止 Spring 版本差异或 mapping 遗漏导致的静默放行。

### 7.3 Actuator 保护

历史问题是 `show-details: always` + `shutdown: enabled` 组合 —— 任何能访问端口的一方都能读到完整连接池/环境变量信息,甚至调用 shutdown 停掉后端。现由 `ActuatorSecurityConfig` 显式收口:

| 端点 | 策略 |
|---|---|
| `/actuator/shutdown` | 仅 `127.0.0.1` / `::1` |
| `/actuator/health` | 公开,但 `show-details: when-authorized` → 外部只见 `UP`/`DOWN` |
| `/actuator/info` | 公开 |
| 其它(含 `metrics`) | 仅本机 |
| 业务 API `/api/**`、`/ws/**` | 放行(依赖绑卡 + CORS + WS TOFU) |

配合 `management.sanitize.keys-to-sanitize` 对 `password`/`secret`/`token`/`private.key` 等全局脱敏。

### 7.4 敏感字段:加密 + 脱敏

| 环节 | 措施 |
|---|---|
| 入库 | AES-256-GCM 加密(`CryptoService`),主密钥落 `%USERPROFILE%\.devnest\master.key` |
| 响应 | 统一返回 `********`;导入文件的脱敏值不会被误当作真实密码 |
| 序列化 | `SensitiveDataLogFilter` 注册 Jackson `BeanSerializerModifier`,字段名命中 `password`/`secret`/`token`/`apikey`/`privatekey`/`credential` 等变体且类型为 `String` 时,值替换为 `***` |
| 日志 | WS token 只留前后 3 位 |

> `SensitiveDataLogFilter` 的边界(代码注释已声明):它拦的是**序列化输出**,拦不住手写的 `log.info("pw={}", password)`。后者靠 `@ToString.Exclude` + 代码审查兜底。

### 7.5 SQL 防护:黑名单,不是白名单

**这是与需求文档不一致的一处,需要明确**:`需求.md` 写的是"内置 SQL 白名单拦截,仅放行 SELECT/SHOW/DESCRIBE/EXPLAIN,根本性杜绝 DDL"。**实际实现是黑名单**:

```java
// common/sql/SqlSanitizer.java
private static final List<Pattern> BLOCKED_PATTERNS = List.of(
    INTO OUTFILE | INTO DUMPFILE | LOAD_FILE | LOAD DATA |   // 文件系统
    SLEEP( | BENCHMARK( | PG_SLEEP( | WAITFOR DELAY |        // 盲注探测
    EXEC | EXECUTE | PREPARE | DEALLOCATE                    // 动态执行
);
```

设计依据(代码注释):**用户已知数据库密码,权限应由数据库自身的账号权限控制**;应用层只阻止"系统级危险操作"。因此 **DML/DDL 是放行的**。

配套细节:

- 长度上限 50,000 字符;
- 先 `stripComments` 去注释再匹配 —— 因为危险写法可在关键字间插块注释绕过 `contains`;
- 关键字一律**正则**匹配(不是 `String.contains`),容忍 `SLEEP (5)`、`LOAD\nDATA` 这类变体;
- 统一 `toUpperCase(Locale.ROOT)`(避免土耳其语环境 `i/I` 转换异常);
- 支持按引号外分号切分多语句,逐条校验。

> 若要真正"杜绝 DDL",应改用只读数据库账号 + 白名单校验,而不是仅依赖应用层黑名单。

### 7.6 Redis 命令防护

见 §5.4,`RedisCommandWhitelist` 为 **Fail-Closed 白名单**,未知命令拒绝,并显式拒绝 `FLUSHALL`/`KEYS`/`CONFIG`/`SHUTDOWN` 等。

## 9. 构建与交付

### 9.1 构建链路

```
scripts/build-jre.ps1  ── jlink 裁剪 JRE 21(约 60MB)
        │                  ⚠️ 模块清单必须含 jdk.unsupported
        ▼                  (缺它 → Spring CGLIB 用到 sun.misc.Unsafe → 启动即
frontend-ui/src-tauri/       NoClassDefFoundError → "Unexpected AOP exception")
  resources/
    ├── devnest-boot.jar  ← mvn package 产物
    └── jre21/            ← jlink 产物
        │
        ▼
npm run tauri build  ──> bundle/nsis/*.exe  +  bundle/msi/*.msi
```

两个入口,**共用** `build-jre.ps1`:

| 入口 | 用途 |
|---|---|
| `build-app.ps1`(根目录) | 本地一键打包,`-SkipBackend` 可跳过 Maven |
| `.github/workflows/build-app.yml` | CI,`windows-2022`,push 到 `main`/`dev` 触发 |

### 9.2 CI 的亮点:打包后 smoke test

CI 在打包前会用**刚生成的 jlink JRE** 真实启动后端:

```
Start-Process jre21/bin/java.exe -jar devnest-boot.jar --spring.profiles.active=dev --server.port=38099
轮询日志直到出现 "Started DevNestApplication",上限 90s
失败则 dump stdout/stderr 并退出
```

这专门防"jlink 漏模块"这类**只在打包后才暴露**的回归 —— 单元测试永远发现不了。

### 9.3 达梦驱动的特殊处理

DM8 JDBC 驱动不在 Maven 中央仓库:

- jar 放在 `backend/lib/DmJdbcDriver18-8.1.3.140.jar`;
- 构建前用 `mvn install:install-file` 装到本地仓库(CI 里失败只 `::warning::`,不中断,降级为"无 DM 支持");
- `devnest-boot` 用 profile `dm-driver` 条件化引入(激活条件 `!skipDm`),CI 可用 `-DskipDm` 跳过。

### 9.4 运行时目录(安装版)

| 内容 | 路径 |
|---|---|
| 配置库 | `%LOCALAPPDATA%\DevNest\data\devnest.mv.db` |
| 流水线工作区 | `%LOCALAPPDATA%\DevNest\data\pipeline\` |
| 加密主密钥 | `%USERPROFILE%\.devnest\master.key` |
| 单实例锁 | `%LOCALAPPDATA%\DevNest\app.lock` |
| 后端日志 | `%TEMP%\devnest-backend.log`(UTF-8) |
| 桌面壳日志 | `%TEMP%\devnest-app.log` |

桌面壳(`src-tauri/src/lib.rs`)负责:

- 拉起后端(优先打包 JRE,回退系统 java),`CREATE_NO_WINDOW` 不弹黑窗;
- 单实例锁:重复启动直接退出,避免多开互抢后端与端口;
- 就绪检测:轮询到后端可用再渲染(`READY_TIMEOUT_SECS = 60`);
- 关闭时先 `POST /actuator/shutdown` 优雅退出,超时(10s)才强杀,避免 H2 数据损坏;
- 路径修复:打包后 Tauri 传入的路径带 `\\?\` verbatim 前缀,`java -jar` 无法打开 → 传参前还原为普通 Win32 路径(历史 bug,见 README)。

## 10. 已知技术债

按"会不会真的咬人"排序,供后续迭代参考。

### 10.1 CI 从不跑测试

```yaml
# .github/workflows/build-app.yml
mvn package -DskipTests -B -q
```

`build-app.ps1` 同样是 `-DskipTests`。结果是**已有的 5 个测试类没有任何自动化执行入口**。建议 CI 增加独立 test 步骤(或去掉 `-DskipTests`)。

### 10.2 CI 触发路径遗漏 `scripts/**`

```yaml
paths:
  - 'backend/**'
  - 'frontend-ui/**'
  - '.github/workflows/build-app.yml'
```

`build-jre.ps1` 恰恰是 README 特别强调"必须含 `jdk.unsupported`、本地与 CI 共用"的文件,却**不在触发路径里** —— 改它不会触发 CI,正好漏在最该防的地方。

### 10.3 三个模块零测试

| 模块 | 测试依赖 | 未覆盖的关键代码 |
|---|---|---|
| `devnest-common` | ✅ | `CryptoService` / `KeyManager`(加密核心)无测试 |
| `devnest-core` | ✅ | — |
| `devnest-datasource` | ✅ | — |
| `devnest-redis` | ✅ | — |
| **`devnest-tunnel`** | ❌ 无 | `SshTunnelInstance`(状态机+重连)、`PortAllocator` |
| **`devnest-console`** | ❌ 无 | `WsTokenManager`(**一次性 token 握手**)、`ConsoleSessionManager` |
| **`devnest-pipeline`** | ❌ 无 | `PipelineExecutionEngine`、`LocalProcessExecutor`、`ProcessKiller` |

风险不对称的是 `WsTokenManager`(认证凭据签发/校验)与 `CryptoService`(全部敏感字段加解密):**纯逻辑、零依赖、测试成本最低,收益最高**,应优先补。

### 10.4 `RedisPoolFactory.shutdown()` 未挂 `@PreDestroy`(已修复)

原问题:`shutdown()` 方法存在,但没有任何注解,Spring 不会把它当作销毁回调,应用退出时 Redis 连接池与**其占用的隧道端口**都不会被显式释放。进程退出后 socket 由 OS 回收,所以危害有限,但与 `HikariPoolFactory`/`SshTunnelManager` 等的做法不一致。

已补上 `jakarta.annotation.PreDestroy`:

```java
@PreDestroy
public void shutdown() {
    pools.keySet().forEach(this::destroyPool);
}
```

这条疏漏能长期存在,本身就印证了 §0.2.1 所述的问题:没有统一资源登记表时,漏挂一个回调既不会有编译错误,也不会有测试失败。其余资源是否都挂上了,目前仍只能靠人工核对。

### 10.5 声明但未使用的依赖与设施
