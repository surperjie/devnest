## 0. 本文档的定位

`架构文档` 回答"**机制是怎么设计的**",本文档回答"**现在到底有什么能用**"。

两者视角不同,结论可能看似矛盾。例如缓存:`架构文档` §4.7 会说明 `CacheClusterConfig` 声明了 3 个 Caffeine 缓存及其规格(这是"设计"),而本文档会把它标为 ⚠️ 半实现——因为**没有任何业务代码使用它**(这是"可用性")。**"代码里有"不等于"功能能用"**,本文档只关心后者。

**有冲突时,本档以代码事实为准;若与 `架构文档` 的机制描述冲突,以 `架构文档` 为准**(它承载设计意图,本文档承载可用性判定)。

### 0.1 判定标准

| 标记 | 含义 | 判据 |
|---|---|---|
| ✅ **已实现** | 端到端可用 | 有持久化、有 API、有前端入口、有释放路径 |
| ⚠️ **半实现** | 设施存在但未闭环 | 有 Bean/接口/抽象,但**无消费者**,或**替换不了** |
| ❌ **未实现** | 不存在 | 需求或设计提过,代码里没有 |
| 🔒 **形态受限** | 仅单机形态可用 | 多用户/服务端形态下会失效或出错 |

⚠️ 与 ❌ 的区别很重要:⚠️ 是"**已付出的成本没有产生收益**",❌ 是"还没开始"。前者是技术债,后者是待办。

## 3. 半实现清单(⚠️)—— 已付出成本但未闭环

这一节是本文档的核心。以下设施**已经在代码里**,但没有产生实际作用。

### 3.1 三个接口-实现对缺失装配契约

| 接口 | 实现 | 当前装配 | 后果 |
|---|---|---|---|
| `core/spi/TunnelPortForwarder` | `tunnel/spi/TunnelPortForwarderImpl` `@Component` | 硬编码 | 能解耦,**不能替换** |
| `core/spi/BastionLookupService` | `tunnel/spi/BastionLookupServiceImpl` `@Service` | 硬编码 | 能解耦,**不能替换** |
| `common/context/CurrentUserProvider` | `common/context/LocalUserProvider` `@Component` | 硬编码 | **说法是"只需替换实现",实际替换会 Bean 冲突** |

三者均无 `@ConditionalOnMissingBean`、无 `META-INF/services`、无 `@Primary`。

**这不是抽象不够优雅,而是"注释承诺的能力,代码不具备"**:

```java
// CurrentUserProvider.java:5-8
// 单机形态下实现返回本机登录用户;将来后端部署为多人共用时,
// 只需替换实现(从登录态 / 会话取值),审计与数据源归属等调用方无需改动。
```

新增一个 `SessionUserProvider` 会直接触发 `NoUniqueBeanDefinitionException`。**当前只有一个实现所以"恰好"能启动,这是巧合而非保证。**

### 3.2 有设施无消费者

| 设施 | 位置 | 状态 |
|---|---|---|
| 3 个 Caffeine 缓存 + `@EnableCaching` | `core/cache/CacheClusterConfig` | 全库无 `@Cacheable`/`@CacheEvict`,Cache Bean 无人注入 |
| `okHttpClient` Bean | `core/http/OkHttpConfig` | 无消费者(`http` 模块未实现) |
| `resilience4j-spring-boot3` | 根 POM `dependencyManagement` | **无任何模块引入**,代码无熔断/重试用法 |
| `AI_DISABLED` / `AI_GENERATE_FAILED` | `common/exception/ErrorCode` | `ai` 模块未实现 |

### 3.3 已埋但未启用的双形态开关

| 开关 | 位置 | 状态 |
|---|---|---|
| `DEVNEST_SERVER_ADDRESS` | `application.yml:2` | ✅ 已支持环境变量覆盖,注释写明"部署到服务器时覆盖" |
| `spring.profiles.active=prod` | `application-prod.yml` | ✅ 已支持配置库切换到 MySQL |
| CORS 白名单可配 | `application.yml:47` | ✅ 注释写明"部署到服务器后按实际域名调整" |
| **用户上下文形态切换** | — | ❌ **无任何机制** |
| **鉴权** | — | ❌ 仅 Actuator 有保护,业务 API 全裸 |

**结论**:双形态的"**基础设施层**"已具备切换能力(地址、库、CORS),但"**身份层**"完全缺失。这正是 `架构演进路线` S2 阶段的核心工作。

## 4. 运行时资源清单

以下是从代码中逐个核对的**全部**运行时资源及其释放路径。

| # | 资源 | 持有者 | 释放方式 | 位置 |
|---|---|---|---|---|
| 1 | 配置库连接池 | `core/persistence/PersistencePoolConfig` | Spring 推断调用 `close()` | `PersistencePoolConfig.java:23` |
| 2 | 业务数据源池(N 个) | `core/pool/HikariPoolFactory` | `@PreDestroy onShutdown()` → `destroyAll()`,⚠️ 注解写作全限定名 | `HikariPoolFactory.java:213` |
| 3 | SSH 隧道实例 | `tunnel/tunnel/SshTunnelManager` | `@PreDestroy stopAll()` | `SshTunnelManager.java:141` |
| 4 | 控制台会话 | `console/session/ConsoleSessionManager` | `@PreDestroy closeAll()` | `ConsoleSessionManager.java:118` |
| 5 | 流水线运行 / 子进程 | `pipeline/run/PipelineRunManager` | `@PreDestroy shutdown()` → 逐个 `cancel()` | `PipelineRunManager.java:113` |
| 6 | WS token 清理线程 | `console/ws/WsTokenManager` | `@PostConstruct` 启动 / `@PreDestroy` 停止 | `WsTokenManager.java:61,67` |
| 7 | 统一虚拟线程池 | `core/thread/VirtualThreadExecutorConfig` | `destroyMethod="shutdown"` + `DisposableBean` 等待 3s | `VirtualThreadExecutorConfig.java:32,41` |
| 8 | Redis 连接池(N 个) | `redis/pool/RedisPoolFactory` | `@PreDestroy shutdown()` | `RedisPoolFactory.java:138` |
| 9 | 主密钥 | `common/crypto/KeyManager` | `@PostConstruct` 载入 | `KeyManager.java:25` |

**这 9 处是人工逐文件统计的结果,没有任何自动化手段能保证不遗漏。** 第 8 项(`RedisPoolFactory`)曾长期漏挂 `@PreDestroy`,而编译器、测试、代码审查都没有发现——这直接印证了资源登记表缺失的代价。

> **本文档自身校对时就漏了一次**:`HikariPoolFactory` 的注解写作**全限定名** `@jakarta.annotation.PreDestroy` 而非 `@PreDestroy`,导致按 `@PreDestroy` 搜索时**不匹配**。该条是靠 `destroyAll` 反查才补回的。这说明"用搜索核对资源清单"这种方法本身就有盲区——**同一语义的写法不一致,会直接导致漏检**。而这也解释了为什么"统一登记表"必须由代码(注解/接口)承担,不能靠文本约定。

> 本清单的维护方式:**每次新增运行时资源,必须同步更新本表**。这是当前唯一的"登记"手段。

## 5. 已知的正确性隐患

与"未实现"不同,这些是**已实现但存在缺陷**的部分。

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| 1 | `isFree()` 存在 TOCTOU 竞态:socket 探测后立即关闭,到真正 bind 之间有空窗 | `PortAllocator.java:63-73` | 单用户难触发;**并发建隧道会双分配同一端口** |
| 2 | 控制台会话不校验属主 | `ConsoleSessionManager.java:102-105` | 多用户下可向他人终端写入 |
| 3 | `LocalUserProvider` 取操作系统账号 | `LocalUserProvider.java:21` | 服务端部署后**所有记录 owner/operator 均为同一值**,静默失真 |
| 4 | 数据源 `visibility` 默认 `PUBLIC` 且无过滤逻辑 | `V11__datasource_owner.sql:4` | 归属字段形同虚设 |
| 5 | 缓存设施无消费者 | `CacheClusterConfig` | 阅读噪音,易误判为已启用 |

> 第 1、3 项的共同特征是**静默失败**:不报错、不告警,数据已错。这类问题比"未实现"危险得多。

### 6.1 已具备

| 日志 | ✅ | `SensitiveDataLogFilter`,业务包 DEBUG |

### 6.2 缺口

| 缺口 | 影响 |
|---|---|
| **无资源清单端点** | 运维无法查询"当前有几条隧道 / 几个控制台会话 / 几个连接池 / 占用了哪些端口" |
| **无自定义 HealthIndicator** | `/actuator/health` 不反映隧道、Redis 池、流水线的实际健康度 |
| **业务指标几乎为零** | 仅池维度指标,无隧道数、会话数、SQL 执行数、流水线运行数 |
| **无 traceId / 请求关联** | 跨模块日志无法串联,排查需人工比对时间戳 |
| **无统一资源登记** | 见 §4,资源是否都挂了回调**只能靠人工核对** |

### 6.3 这一节与"最终目标"的关系

用户在 `目标架构` 中提出的诉求——"**资源统一管理**"与"**后续监听维护能获取到所有模块数据**"——其缺口正是本节 6.2 的全部条目。这不是新增需求,而是 **v1.0 设计稿中 `ResourceRegistry` 能力缺失的延续**(见 `架构文档` §0.2.1)。

## 8. 如何核对本文档

本文档所有结论都可以用以下方式复核:

```powershell
# 1. 资源释放回调清单(注意:不要加 @ 前缀)
#    HikariPoolFactory 用全限定名 @jakarta.annotation.PreDestroy,加 @ 会漏检
rg "PreDestroy|PostConstruct" backend -g "*.java"

# 2. 装配机制(预期:除 @Primary(池/ObjectMapper)外无输出)
rg "@ConditionalOn|@Profile|@Primary" backend -g "*.java"

# 3. 缓存消费者(预期:无 @Cacheable 输出)
rg "@Cacheable|@CacheEvict" backend -g "*.java"

# 4. 模块边界强制
mvn -f backend/pom.xml validate
```

**若上述命令输出与本文档不符,以命令输出为准,并应同步修订本文档。**
