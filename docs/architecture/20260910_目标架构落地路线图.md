
## 1. 五条规划铁律

规划的价值在于**约束顺序**。以下五条是本路线图的不可协商项:

### 铁律 1:级别不可跨越

**L2 未达成前,不投入 L3/L4 的任何建设。**

原因:L4 的全部"自动拦截"(ArchUnit、fitness function、资源自检)都以**测试被强制执行**为运行载体。CI 跳过测试时,L4 的所有设计都退化为"写在文档里的愿望"——这正是 v1.0 的处境:设计了"三重防漏登记防线",而防线 2 依赖的测试基类不存在、CI 跑 `-DskipTests`。

### 铁律 2:先立门禁,再立规则

每条新增约束必须**先有执行载体,后有规则内容**。顺序反了会得到"守不住的约束",最终被绕过并失去权威。

具体:`P0` 先把 ArchUnit 跑起来(哪怕只有 1 条规则),`P1`–`P4` 再把规则逐条加进去。

### 铁律 3:每阶段的出口判据必须机器可验

阶段完成与否**不由主观判断**。每个阶段的门禁都必须是"故意做错 → 构建变红"这类**可执行**验证。写不出机器判据的任务,不予立项。

### 铁律 4:不碰业务逻辑的批次优先

`P0` 全部工作在构建配置与测试基础设施,**零业务代码改动**。这是投入产出比最高的部分,也是唯一"没有任何功能风险"的部分。**先把它做掉。**

### 铁律 5:阶段可暂停,不可倒退

允许在任一阶段停下(单机自用仍可用),但**已建立的约束不得拆除**。为此每个阶段附"锁死清单"(§8),记录该阶段建立的不可回退项及守护者。

### P1 · 装配与形态 —— S2 的前置项

> **出口:同一 jar,两种形态,业务代码零改动。**

**为什么排第二**:`架构演进路线` 的判断是对的——S2 的主要工作量在**装配层与安全层,不在业务层**(业务抽象已就绪:`CurrentUserProvider` 已定义、`V10`/`V11` 已含 `operator`/`owner`/`visibility`)。装配层是其余所有动作的前提。

**前置依赖**:P0(没有测试与 ArchUnit,P1 的形态自检无法被守护)。

| # | 任务 | 落点 | 交付物 |
|---|---|---|---|
| 1.1 | 引入 `devnest.mode = local \| server` 属性 + **形态元注解**(`@LocalMode` / `@ServerMode`) | 新增 `core/mode/` | 形态单一事实源 |
| 1.2 | **形态与 profile 正交化**:`application-desktop.yml` 退役,其内容(H2 文件库 + 日志收敛)改为 LOCAL 形态默认环境 | `devnest-boot/src/main/resources/` | 解开耦合 |
| 1.3 | 三个 SPI 补 `@ConditionalOnMissingBean`,从"能解耦"升级为"**可替换**" | `core/spi/TunnelPortForwarder`、`core/spi/BastionLookupService`、`common/context/CurrentUserProvider` | 装配契约 |
| 1.4 | 模块自动配置(`AutoConfiguration.imports`),模块**自描述** Bean | 各模块 `resources/META-INF/spring/` | 免启动类无差别扫描 |
| 1.5 | `ServerModeConsistencyCheck`:**前提被打破即启动失败** | 新增 `core/mode/` | 不静默失效 |
| 1.6 | 负向用例 **N1/N3/N7** 入库 | ArchUnit + 集成测试 | 退化可拦截 |

**关于 1.2 的说明**:现状 `spring.profiles.active` **同时承担两种语义**——`dev`/`prod` 是**环境**,而 `desktop` 实际是**交付形态**。形态挂在 profile 上会导致"LOCAL 形态 + 生产日志"这类组合必须新增 profile,维度爆炸。正交化后:

```
devnest.mode       = local | server    ← 决定装配(装哪些 Bean)
spring.profiles.active = dev | prod     ← 决定环境值(库、日志、地址)
```

这同时消除了早期设计草稿引入的 `application-local.yml`/`application-server.yml` 与现状的命名冲突。

**阶段门禁**

| 判据 | 验证动作 | 期望 |
|---|---|---|
| 双形态可切换 | 同 jar,两组启动参数 | 形态正确切换,业务代码零改动 |
| 本地不退化 | LOCAL 形态端到端 | 与 S1 **完全一致** |
| 不静默失效 | SERVER 形态下装配 `LocalUserProvider` | **启动失败并指明原因**(C6/N3) |
| SPI 可替换 | 新增一个 `TunnelPortForwarder` 实现 | 生效,无需改 tunnel 模块 |
| 形态语义不散落 | 在业务类上直接用裸 `@ConditionalOnProperty` | ArchUnit **红**(C10/N7) |

**风险与对策**

| 风险 | 对策 |
|---|---|
| **为服务端安全牺牲本地体验**(最典型失败) | `matchIfMissing = true` 让**默认即 LOCAL**;出口判据含"本地形态与 S1 完全一致" |
| 形态判断散落到业务代码 | 元注解 + C10 ArchUnit 断言双保险 |

**规模**:M(约 6–9 人日)

### P2 · 治理纵深(看得见)

> **出口:资源与运行时有总账,且漏登记会被机器发现。**

**前置依赖**:P1(资源登记需按形态区分归属)。

| # | 任务 | 落点 | 交付物 |
|---|---|---|---|
| 2.1 | `ManagedResource` 描述符 + `ResourceRegistry`(register/updateState/unregister/snapshot/countByType) | 新增 `core/resource/` | 资源总账 |
| 2.2 | **9 类资源逐个登记**(配置库池、业务池、隧道实例、控制台会话、流水线运行、WS token 清理线程、虚拟线程池、Redis 池、主密钥) | 各持有者 `@PreDestroy` **保持不变** | 登记表 |
| 2.3 | 启动自检:资源类型集合 vs 预期集合,缺失即 WARN(可配 Strict) | `core/resource/` | 防漏登记 |
| 2.4 | `ResourceRegistryTestBase` 生效,断言"所有资源类型已登记" | 测试基座 | **防线 2**(v1.0 的空壳在此兑现) |
| 2.5 | `/actuator/resources` 端点 + **11 项指标**(`devnest.<domain>.<metric>`)+ **3 个 HealthIndicator** | `core/observability/` | 全局视图 |
| 2.6 | `TraceIdFilter`(servlet) + **新建 `logback-spring.xml`** + 异步任务 MDC 显式传递 | `core/log/`、`resources/` | 跨线程可串联 |
| 2.7 | 优雅关闭链路升级:资源状态同步 + 关闭报告 | `core/resource/` | 关闭可量化 |
| 2.8 | 负向用例 **N2/N8** 入库 | 集成测试 | 退化可拦截 |

**两条必须写死的设计约束**(承自 v1.0 §3.1,不可动摇):

1. **登记 ≠ 接管释放**。资源在登记表注册自己,**释放仍由各模块 `@PreDestroy` 执行**。登记表只提供全局视图与遗漏检测。理由:模块最了解自己的资源,失败也不牵连他人。
2. **描述符不得携带敏感值**。`ManagedResource.attributes()` 只放属性(主机/端口/数量),不放密码/token/密钥——否则登记表本身成为泄露面。

**必须纠正的一处 v1.0 事实错误**:v1.0 §4.5 称 `SensitiveDataLogFilter` 可作为 traceId 载体。核实后不成立——它是 **Jackson 响应体字段脱敏器**(`SensitiveDataLogFilter.java:36-83`),源码注释自己写明"代码里手动 `log.info` 的泄露本 Filter 不能覆盖",**接不进 MDC**。task 2.6 必须新建 `TraceIdFilter`,不得复用。

**阶段门禁**

| 判据 | 验证动作 | 期望 |
|---|---|---|
| 资源可视 | `GET /actuator/resources` | 返回 9 类资源 |
| 漏登记可发现 | 新增一个未登记的资源容器 | 启动 WARN + 测试 **红**(C5/N2) |
| 关闭可量化 | `POST /actuator/shutdown` 后查快照 | 所有资源状态 `RELEASED`,无残留 |
| traceId 跨线程 | 提交异步任务后断言 MDC | traceId **未丢失**(C12/N8) |
| 重复防漏 | 核对 | 能力清单 §4 的 9 项与登记表**逐项一致** |

**风险与对策**

| 风险 | 对策 |
|---|---|
| 登记表与人工清单不一致 | 以 **`ResourceRegistryTestBase` 断言**为准,文档退化为参考(机器是唯一事实源) |

**规模**:L(约 10–14 人日)

### P3 · 安全与隔离(管得住)

> **出口:权限可拦、操作可审、密钥可换、故障可隔。**

**前置依赖**:P1(鉴权与归属校验都需形态装配)。

| # | 任务 | 落点 | 交付物 |
|---|---|---|---|
| 3.1 | **鉴权锚点按形态装配**:替换 `ActuatorSecurityConfig` 的 `anyRequest().permitAll()` | `ActuatorSecurityConfig.java`(现 `:59`) | 业务 API 保护 |
| 3.2 | 数据可见性过滤落地:`owner`/`visibility` 生效 | `devnest-datasource` 查询层 | 归属隔离 |
| 3.3 | 状态归属校验:控制台会话 / 隧道 / 流水线按用户隔离 | 各 Manager | 防越权 |
| 3.4 | **`PortAllocator` 修复 TOCTOU 竞态**(探测与占位需原子) | `PortAllocator.java:63-73` | 并发正确性 |
| 3.5 | 通用操作审计切面 + `audit_event` 表(who/when/what/target/result/ip/trace_id) | 新增 `core/audit/` + Flyway 迁移 | 操作可审 |
| 3.6 | **密钥 `keyId` 化 + 轮换**:密文自描述,支持多密钥并存与批量重加密 | `CryptoService`、`KeyManager` | 密钥可运维 |
| 3.7 | resilience4j 落地:**工具级 bulkhead / 熔断 / 限流** | `core/` + 各工具 | 故障隔离 |
| 3.8 | SBOM(CycloneDX)接入 CI | CI | 供应链 |

**关于 3.1**:那一行 `permitAll()` 依赖的前提是"仅绑 127.0.0.1 + CORS + TOFU",而 **SERVER 形态恰恰就是打破这个前提的那一刀**。必须在 LOCAL 形态保持直通(**不牺牲本地零配置**),在 SERVER 形态走完整鉴权。

**关于 3.6(新发现的真问题)**:当前密文格式为 `base64(IV || CT || TAG)`,**没有 keyId**。这意味着**主密钥不可轮换**——一旦更换 `master.key`,所有已加密的密码密文全部无法解密,且无版本号可做渐进迁移。单机自用可忍(用户重录),但 SERVER 形态下这是**不可运维的设计**。

**关于 3.7**:`resilience4j-spring-boot3` 已在根 POM 声明但**全库零使用**(典型"已付成本无收益")。落地方向是**工具级隔离**而非全局限流:一个工具(如 tunnel)阻塞,不得耗尽全局虚拟线程池而拖垮其他工具。

**阶段门禁**

| 判据 | 验证动作 | 期望 |
|---|---|---|
| 鉴权生效 | SERVER 形态未登录访问业务 API | **401**;LOCAL 形态直通 |
| 归属隔离 | 用户 A 访问用户 B 的会话/数据源 | 拒绝 |
| 并发正确 | 并发发起多条隧道创建 | 端口**不重复分配**(TOCTOU 已修) |
| 审计可串联 | 一次写操作 | `audit_event` + 日志可经 traceId 查到全链路 |
| 密钥可轮换 | 更换主密钥 | 旧密文**仍可解密**,新写入用新密钥 |
| 故障被隔离 | 人为阻塞 tunnel 模块 | 其他工具 API **仍正常响应** |

**风险与对策**

| 风险 | 对策 |
|---|---|
| 加了鉴权导致本地也要登录 | LOCAL 形态 `permitAll` 保持;出口判据含"LOCAL 直通" |
| 密钥轮换改动加密格式,**存量密文兼容** | 新格式带 `keyId`,旧密文按"无前缀 = v1"兼容读取,提供批量重加密命令 |
| 审计表无限增长 | `audit_event` 保留期策略 + 分区/清理任务(与 Flyway expand-contract 配合) |

**规模**:L(约 10–15 人日)

| 4.3 | **Flyway expand-contract 规范** + 迁移测试(旧应用 + 新 schema 可启动) | `db/migration/` + CI | 变更可回退 |
| 4.4 | 兼容性矩阵(应用版本 × schema 版本 × 前端版本) | `docs/ops/` | 防错配启动 |
| 4.5 | `docs/ops/发布与回滚.md`:回滚判据、命令、验证步骤 | `docs/ops/` | 回滚可执行 |

**回溯 ADR 的候选清单**(建议首条即立项):

| 编号 | 决策 |
|---|---|
| 0001 | 单进程多模块,而非微服务 |
| 0002 | 登记 ≠ 接管资源释放 |
| 0003 | 形态与 profile 正交 |
| 0004 | 不做 URL 版本化(改字段级兼容策略) |
| 0005 | 不做集群 / 不做 trace 后端(及单实例重启语义) |

**关于 4.3 的关键含义**:"可回滚"在数据库层面的真正含义是——**回滚 = 回退应用版本,而不是回退 schema**。因此每条迁移必须**前向兼容**:任何时候回退应用版本,新 schema 仍能被旧代码使用。破坏性变更必须拆为 expand(加新列)→ migrate(回填/双写)→ contract(删旧列)三步。

**阶段门禁**

| 判据 | 验证动作 | 期望 |
|---|---|---|
| 决策可追溯 | 任一"不做 X"能在 `docs/adr/` 找到编号 | 存在 |
| 弃用受约束 | 新增无 `since` 的 `@Deprecated` | ArchUnit **红**(C13) |
| 迁移前向兼容 | 回退应用版本到上一版 | 新 schema 下**启动成功且功能可用** |
| 兼容矩阵有效 | "新 jar + 不兼容旧库"启动 | **启动自检失败** |

**风险与对策**

| 风险 | 对策 |
|---|---|
| ADR 写成形式主义 | 只回溯**已有争议/边界决策**(上表 5 条),不为写而写 |
| 存量 11 个脚本已是单向,难追溯 | 不重写历史;从**新迁移开始**执行 expand-contract,存量标注为"legacy forward-only" |

**规模**:M(约 5–8 人日)

### P5 · 扩展点闭环 —— L4 / S3 的兑现

> **出口:新增工具,平台零改动,治理自动继承。这是"底座"的最终证明。**

**前置依赖**:P2(资源/指标/健康)+ P3(隔离/审计)。

| # | 任务 | 落点 | 交付物 |
|---|---|---|---|
| 5.1 | `DevNestTool` 扩展点契约(工具元信息、生命周期、健康、扩展点声明) | 新增 `core/tool/` | 接入契约 |
| 5.2 | `ToolRegistry` + **治理联动**(注册即自动纳入资源视图/指标/健康) | `core/tool/` | 接入即继承治理 |
| 5.3 | 将现有 5 个模块**改造为工具**(tunnel / console / datasource / redis / pipeline) | 各模块 | 验证契约可用 |
| 5.4 | **fitness function(C11)**:新增测试工具模块 → 断言其资源/指标/健康**自动出现**,否则 CI 红 | 集成测试 | **零改动可验** |
| 5.5 | 前端工具装配:工具列表由平台下发(而非硬编码菜单) | `frontend-ui` | 端到端零改动 |

**设计要点(承自 v1.0 §5.2)**:扩展点**不是注册表,是治理能力的接入契约**。工具声明"我是谁",平台自动赋予"资源视图 + 指标 + 健康 + 生命周期编排 + 释放"。这是"平台管治理、工具管业务"的落点,也是大厂底座级架构的核心特征。

**阶段门禁**

| 判据 | 验证动作 | 期望 |
|---|---|---|
| 零改动接入 | 新增一个最小测试工具模块 | **平台代码零改动** |
| 治理自动继承 | 查 `/actuator/resources`、指标、health | 新工具的资源/指标/健康**自动出现** |
| 生命周期编排 | 启停平台 | 工具随平台启停,释放被登记 |
| 零改动可验(fitness) | 运行 C11 断言 | 通过;若平台需改动则 CI **红** |

**风险与对策**

| 风险 | 对策 |
|---|---|
| 过早抽象(无第二个消费者) | **P5 排在最后正是为此**。`架构演进路线` §4.2 已论证:没有第二个实现时,扩展点是纯抽象成本。S3 才有真实消费者 |
| 改造现有 5 模块引入回归 | P0 的测试门禁是前提;分批改造,每批跑全量回归 |

**规模**:L(约 8–12 人日)

## 4. 依赖与并行

```
        ┌─────────────────────────────────────────────┐
        │              P0 地基夯实                     │
        │   (无前置,零业务改动,ROI 最高)              │
        └───────────────┬─────────────────────────────┘
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
   ┌─────────────┐            ┌─────────────┐
   │ P1 装配形态  │            │ P4 演进纪律  │  ← 仅依赖 P0,可并行
   │  (S2 前置)   │            │  (改/删纪律) │
   └──────┬──────┘            └─────────────┘
          │
    ┌─────┴─────┐
    ▼           ▼
┌────────┐  ┌────────┐
│P2 治理 │  │P3 安全 │   ← P2/P3 均只依赖 P1,可并行
│(看得见)│  │(管得住)│
└───┬────┘  └───┬────┘
    │           │
    └─────┬─────┘
          ▼
   ┌─────────────┐
   │ P5 扩展点闭环│  ← 需 P2 + P3 的治理能力齐备
   │ (L4 / S3)   │
   └─────────────┘
```

**关键路径(决定总时长)**:`P0 → P1 → P2 → P5`
**可并行旁路**:`P4`(任意时刻插入,只要 P0 完成)

> **不要并行 P2 与 P5**。P5 的 fitness function 要断言"资源/指标/健康自动出现",而这三个能力由 P2 提供。P2 未完成时,P5 的验收无法成立。

## 5. 里程碑

| 里程碑 | 达成条件 | 意义 |
|---|---|---|
| **M1 · 门禁可信** | P0 出口判据全部通过 | 后续所有"自动拦截"有了运行载体。**跨过这一条,自检体系才不是沙上建塔** |
| **M2 · 双形态可行** | P1 + P3 出口通过 | S2 达成:同一 jar 双形态,身份/鉴权/隔离生效 |
| **M3 · 底座成型** | P2 + P4 + P5 出口通过 | **L4 达成**:看得见 + 管得住 + 变更可治理 + 新工具零改动接入 |

## 6. 规模与优先级

| 阶段 | 规模 | 人日(估) | ROI 排序 | 说明 |
|---|---|---|---|---|
| P0 | M | 8–12 | **① 最高** | 零业务风险 + 让后续全部可被信任 |
| P4 | M | 5–8 | ② | 成本低、可并行、防"改不动" |
| P1 | M | 6–9 | ③ | S2 的地基,决定形态能否切换 |
| P2 | L | 10–14 | ④ | 工作量最大的一批,但直接兑现"可观测" |
| P3 | L | 10–15 | ⑤ | 安全与隔离,含 TOCTOU 与密钥两个硬骨头 |

**合计约 47–70 人日**(单人节奏,含调试与返工)。

> 估算前提:单人开发、AI 辅助、无历史包袱以外的阻塞。**P0 是唯一"建议立即启动"的阶段**——它不触碰业务代码,即使后续路线调整,成果也不会浪费。

## 8. 各阶段的"锁死"清单(防倒退)

每阶段建立的约束**不得在后续被拆除**。拆除即视为违反不变量(§6 of v2.0)。

| 阶段 | 锁死项 | 守护者 |
|---|---|---|
| P0 | CI 不得出现 `-DskipTests`;四道门禁阈值不得下调;ArchUnit 规则不得删除 | CI 配置评审 + ArchUnit 自检 |
| P1 | 形态必须由 `devnest.mode` 决定;业务代码不得直接使用 `@ConditionalOnProperty` | C10 ArchUnit 断言 |
| P2 | 新增资源必须登记;描述符不得携带敏感值 | C5 启动自检 + `ResourceRegistryTestBase` |
| P3 | 业务 API 在 SERVER 形态不得裸放行;密文必须带 `keyId` | 鉴权集成测试 + 加密格式测试 |
| P4 | 迁移必须前向兼容;`@Deprecated` 必须带 `since` | C9 迁移测试 + C13 ArchUnit |
| P5 | 新工具接入不得要求修改平台代码 | **C11 fitness function** |

> **注意最后一行**:P5 的锁死项由 fitness function 守护——**这是整个体系的自证**:一个能守护自身"零改动"性质的架构,才配称底座。

## 9. 明确不纳入本路线图的事

以下均为**经过考虑的否定**(详见 `目标架构 v2.0` §7),不列为待办,以免被误读为"遗漏":

| 不做 | 一句话理由 |
|---|---|
| 分布式 / 集群 | 单实例 + 外置库足以支撑内网自用工具平台;单实例重启语义按 R5 显式声明 |
| 微服务拆分 | 仍是单进程多模块;模块化解决开发期边界,不是部署隔离 |
| 运行时热插拔 jar | 工具在构建期接入;类加载器隔离的复杂度远超收益 |
| 多租户(B2B SaaS) | 只做多用户共享实例,不做多组织强隔离 |
| URL 版本化(`/v1/`) | 无独立发布周期的第三方消费者,改用字段级兼容策略 |
| trace 后端(Jaeger/Zipkin) | 保留 traceId + spanId 与结构化日志,不引入额外部署组件 |
| 全局限流(网关式) | 改用工具级隔离(bulkhead),更贴合"多工具互不干扰" |

**范围守卫**:本路线图的任何阶段,**不得**以"补齐上面 7 项"为理由扩张。若确需纳入,应先按 P4 的 ADR 流程立决策记录。
