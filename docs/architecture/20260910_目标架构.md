## 0. 本文档的定位

本文档回答三个问题:

1. **双形态如何在同一份代码中正确切换**(S2 目标)
2. **运行时资源如何被统一管理**(贯穿 S2/S3)
3. **运维如何获取全部模块的数据**(贯穿 S2/S3)

第 2、3 点是本文档重心,也是当前架构**最大的结构性缺口**。它们不是新增需求,而是 v1.0 设计稿中 `ResourceRegistry` 能力的延续——该能力实现时被放弃,`架构文档` §0.2.1 已定性为"能力缺失"。

**阅读约定**:文中接口、端点、模块均标注 `[目标]`;引用现有代码标注 `[现状]`。

## 1. 目标形态

### 1.1 双形态

**一个构建产物,两种装配**。形态由启动参数决定,不由代码分支决定。

```
                    ┌─────────────────────────────┐
                    │   同一份 devnest-boot.jar    │
                    └──────────────┬──────────────┘
                                   │
              devnest.mode=local(默认)    devnest.mode=server
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                          ▼
    ┌───────────────────┐                     ┌───────────────────┐
    │  LOCAL 形态        │                     │  SERVER 形态       │
    │  仅回环、单用户      │                     │  内网、多用户       │
    │  无鉴权、全量可见    │                     │  完整鉴权、按归属可见 │
    │  桌面壳拉起         │                     │  浏览器访问         │
    └───────────────────┘                     └───────────────────┘
```

### 1.2 工具巢穴

S3 目标形态:平台提供治理,工具提供业务。

```
┌──────────────────────────────────────────────────────────────┐
│                      DevNest 平台(治理层)                    │
│  身份 · 资源治理(Registry) · 可观测(指标/健康/资源视图)        │
│  形态装配 · 扩展点契约(DevNestTool)                           │
├──────────────────────────────────────────────────────────────┤
│                     工具层(业务)                              │
│  tunnel  console  datasource  redis  pipeline                │
│  ────────────────────────────────────────────                 │
│  [目标] http   [目标] ai   [目标] 未来接入的任意工具            │
└──────────────────────────────────────────────────────────────┘
```

关键性质:**新增工具对平台零改动**。这是 S3 的验收标准,也是后续各设计的共同约束。

## 2. 核心设计一:形态装配模型

### 2.1 问题

`[现状]` 全库 `@ConditionalOn*` 数量为 **0**。所有 Bean 无条件注册,系统里**没有"形态"这个概念**。任何"本地装 A、服务端装 B"的需求,都只能靠 `if (isServer())` 散落各层。

### 2.2 设计:形态判断集中一处,且默认 LOCAL

#### 2.2.1 形态元注解

```java
// core/condition/  [目标]
@Target({ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
@ConditionalOnProperty(name = "devnest.mode", havingValue = "local", matchIfMissing = true)
public @interface ConditionalOnLocalMode { }

@Target({ElementType.TYPE, ElementType.METHOD})
@Retention(RetentionPolicy.RUNTIME)
@ConditionalOnProperty(name = "devnest.mode", havingValue = "server")
public @interface ConditionalOnServerMode { }
```

要点:

- **`matchIfMissing = true` 加在 LOCAL 上**:未配置时默认本地形态,保证单机零配置可用(演进不变量 7)。这是刻意的默认值选择。
- **业务模块不得直接用 `@ConditionalOnProperty`**,必须用这两个元注解。形态语义集中一处,未来新增形态只改 `core/condition`。

#### 2.2.2 模块自描述

`[目标]` 每个含形态相关 Bean 的模块,用 Spring Boot 自动配置声明自己:

```
tunnel/src/main/resources/META-INF/spring/
    com.devnest.tunnel.autoconfigure.TunnelAutoConfiguration.imports
```

好处:模块**自描述**,不再依赖启动类无差别扫描;可被 `@ConditionalOn*` 精确控制;装配顺序可显式声明。

`[现状]` 无 `AutoConfiguration.imports`;`DevNestApplication` 在 `com.devnest` 顶层包,扫描全部模块。

#### 2.2.3 装配契约

`[现状]` 三个 SPI 实现硬编码,替换会 Bean 冲突(`能力清单` §3.1)。

`[目标]` 提供方模块的实现改为**可覆盖的默认实现**:

```java
// tunnel/autoconfigure/TunnelAutoConfiguration  [目标]
@AutoConfiguration
public class TunnelAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean(TunnelPortForwarder.class)
    public TunnelPortForwarder tunnelPortForwarder(SshTunnelManager m, PortAllocator a) {
        return new TunnelPortForwarderImpl(m, a);
    }
}
```

改造范围:

| 接口 | 默认实现 | 目标装配 |
|---|---|---|
| `TunnelPortForwarder` | `TunnelPortForwarderImpl` | `@Bean` + `@ConditionalOnMissingBean` |
| `BastionLookupService` | `BastionLookupServiceImpl` | `@Bean` + `@ConditionalOnMissingBean` |
| `CurrentUserProvider` | `LocalUserProvider` | `@Bean` + `@ConditionalOnLocalMode` |

`CurrentUserProvider` 不同:它不是"默认可覆盖",而是"**按形态二选一**",故用形态注解而非 `@ConditionalOnMissingBean`。

### 2.3 形态差异矩阵

| 关注点 | LOCAL | SERVER | 实现位置 |
|---|---|---|---|
| 绑定地址 | `127.0.0.1` | 可配 | `application-{mode}.yml` |
| 用户上下文 | `LocalUserProvider` | `SessionUserProvider` | `common/context` |
| 鉴权 | 边界收敛 | 完整链路 | `common/security` |
| 数据可见性 | 全量 | 按 `owner`/`visibility` | 各业务模块查询层 |
| 状态归属 | 无归属(全局) | 按用户 | 见 §3 |
| 配置库 | H2 / MySQL | MySQL | profile |
| 前端 | 桌面壳 | 浏览器 | 前端构建 |

### 2.4 防退化硬约束:不静默失效

**服务端形态下若装配了本地实现,必须启动即失败。**

`[现状]` `LocalUserProvider` 的前提是"仅绑回环",该前提在服务端形态下被打破,但代码**无任何防护,会静默写错 `owner`/`operator`**。

`[目标]` 启动期做形态一致性校验:

```java
// 伪代码  [目标]
@Component
@ConditionalOnServerMode
class ServerModeConsistencyCheck implements ApplicationRunner {
    void run() {
        if (context.getBean(CurrentUserProvider.class) instanceof LocalUserProvider) {
            throw new IllegalStateException(
                "服务端形态不允许装配 LocalUserProvider:所有 owner/operator 将写入同一账号");
        }
        // 同类校验:鉴权链路是否就位、绑定地址是否仍为回环、visibility 过滤是否生效
    }
}
```

对应**演进不变量 8:不静默失效**。

## 3. 核心设计二:资源统一管理

> 本文档最重要的设计,`ResourceRegistry` 能力缺失的补偿方案。

### 3.1 先解决一个矛盾

两处文档对"统一资源管理"给出**看似对立**的结论:

| 来源 | 结论 | 理由 |
|---|---|---|
| `架构文档` §0.2.1 | `ResourceRegistry` 缺失 = **能力缺失** | 无全局视图,漏挂回调无人发现 |
| `架构文档` §4.3 | 各模块自治 = **取舍是对的** | 资源类型多样,统一治理要处理顺序与失败 |

**两者都对,但谈的不是同一件事。** 澄清:

| 职责 | 应由谁负责 | 理由 |
|---|---|---|
| **释放执行**(调 `close()`/`stop()`) | **各模块自治** | 模块最了解自己的资源;失败只影响自己 |
| **登记与可见**(知道"有哪些资源") | **统一登记表** | 运维需要总账;遗漏必须能被发现 |

> **登记 ≠ 接管释放。**

各模块 `@PreDestroy` 保持原样(`[现状]` 已有 9 处,见 `能力清单` §4),**不被平台接管**;新增登记表只负责"记账"与"查账"。这个调和方案保留两种设计的优点,且**不引入释放顺序问题**——释放路径没变。

### 3.2 资源描述符

```java
// core/resource/  [目标]
public interface ManagedResource {

    /** 资源类型,用于分组,如 ssh-tunnel / jdbc-pool / console-session */
    String resourceType();

    /** 资源唯一标识 */
    String resourceId();

    /** 类型相关属性(端口、库名、目标地址...),供运维查看 */
    Map<String, Object> attributes();

    /** 状态 */
    ResourceState state();   // ACTIVE / RELEASING / RELEASED / FAILED

    /** 归属用户:SERVER 形态用于隔离与审计;LOCAL 返回 null */
    default String owner() { return null; }

    /** 创建时间 */
    Instant createdAt();
}
```

**硬性约束**:

- **不强制资源类实现此接口**(避免侵入)。资源持有者构造描述符并注册即可。
- `attributes()` 只放**非敏感**信息。密钥、密码、token **禁止**进入描述符——该数据会暴露到运维端点。

### 3.3 注册中心

```java
// core/resource/  [目标]
public interface ResourceRegistry {

    void register(ManagedResource resource);

    void updateState(String resourceType, String resourceId, ResourceState state);

    void unregister(String resourceType, String resourceId);

    /** 全局快照,供运维端点使用 */
    ResourceSnapshot snapshot();

    /** 按类型分组统计 */
    Map<String, Integer> countByType();
}
```

实现为单例 Bean,线程安全(`ConcurrentHashMap`)。模块注入后注册,平台不感知具体模块。

### 3.4 登记点与资源类型

`[目标]` 资源类型清单(基于 `能力清单` §4 的现状盘点):

| 类型 | 登记者 | 释放者(不变) | 关键属性 |
|---|---|---|---|
| `config-db-pool` | `PersistencePoolConfig` | Spring 推断 `close()` | 活跃/空闲连接数 |
| `biz-db-pool` | `HikariPoolFactory` | `@PreDestroy destroyAll()` | datasourceId、池大小、使用率 |
| `ssh-tunnel` | `SshTunnelManager` | `@PreDestroy stopAll()` | bastionId、本地端口、状态 |
| `console-session` | `ConsoleSessionManager` | `@PreDestroy closeAll()` | wsSessionId、consoleId、目标地址 |
| `pipeline-run` | `PipelineRunManager` | `@PreDestroy shutdown()` | runId、pipelineId、当前步骤 |
| `ws-token-cleaner` | `WsTokenManager` | `@PreDestroy stopCleaner()` | 清理间隔 |
| `virtual-executor` | `VirtualThreadExecutorConfig` | `destroyMethod` + `DisposableBean` | — |
| `redis-pool` | `RedisPoolFactory` | `@PreDestroy shutdown()` | instanceId、隧道端口 |
| `master-key` | `KeyManager` | 无(JVM 生命周期) | 密钥路径(不含密钥值) |

### 3.5 如何防止"漏登记"

这是 `ResourceRegistry` 存在的**唯一理由**——若不能防漏,它只是装饰。

`[现状]` 的教训:`RedisPoolFactory.shutdown()` 存在却漏挂 `@PreDestroy`,编译器、单测、代码审查**全部没有发现**。

`[目标]` 三重防线:

| 防线 | 手段 | 时机 |
|---|---|---|
| **1 启动自检** | 扫描容器内"资源容器型" Bean(`Map`/`Set` 等),与登记表比对;未登记则 WARN 并降级健康端点 | `ApplicationReadyEvent` |
| **2 测试守护** | 提供测试基类,断言登记表非空且资源类型集合与预期一致 | CI |
| **3 文档登记** | `能力清单` §4 人工清单,作为评审参照 | 设计评审 |

> **防线 2 最关键**:它把"人工核对"变成"自动化守护",是 S1→S3 的质变。

### 3.6 与释放链路的衔接

`[现状]` 优雅关闭链路(`架构文档` §4.4)保持不变:

```
Tauri → POST /actuator/shutdown → graceful 停机 → Bean 销毁 → 各 @PreDestroy
```

`[目标]` 增加**登记表状态同步**:

- 资源释放时,`@PreDestroy` 内调 `registry.unregister(...)`;
- 容器关闭完成时若某资源仍为 `ACTIVE`,记 WARN 并计入关闭报告;
- **提供"关闭是否干净"的可验证结论**,而不是只看进程是否退出。

## 4. 核心设计三:全局可观测性

> 用户诉求:"后续如果要监听维护能获取到所有模块数据"。

### 4.1 设计原则:平台零改动

可观测性的**验收标准不是"有端点",而是"新增模块自动被纳入,平台不改代码"**。因此四个维度都必须基于**框架扩展点**,而非平台硬编码:

| 维度 | 扩展机制 | 模块要做什么 | 平台要做什么 |
|---|---|---|---|
| 资源 | `ResourceRegistry.register()` | 登记 | **无** |
| 指标 | Micrometer `MeterRegistry` | 注入并注册 | **无** |
| 健康 | `HealthIndicator` 接口 | 实现并注册为 Bean | **无** |
| 日志 | SLF4J MDC | 使用 `log.xxx` | 提供 traceId 注入 |

### 4.2 观测维度一:资源视图

`[目标]` 新增 Actuator 端点 `GET /actuator/resources`:

```json
{
  "generatedAt": "2026-09-10T12:00:00Z",
  "mode": "local",
  "summary": { "ssh-tunnel": 3, "biz-db-pool": 2, "console-session": 1 },
  "total": 6,
  "resources": [
    {
      "type": "ssh-tunnel",
      "id": "bastion-3",
      "state": "ACTIVE",
      "createdAt": "2026-09-10T11:52:13Z",
      "attributes": { "localPort": 10423, "target": "10.0.0.5:22" }
    }
  ]
}
```

**这是"运维获取所有模块数据"最直接的落地**。`[现状]` 该能力完全不存在。

安全策略:

- LOCAL 形态:仅本机可见(沿用现有 IP 分级策略);
- SERVER 形态:需管理员权限。

### 4.3 观测维度二:指标

`[现状]` 仅 `HikariPoolFactory` 接入 Micrometer(池级指标),无业务指标。

`[目标]` 统一命名规范 `devnest.<domain>.<metric>`:

| 指标 | 类型 | 模块 | 说明 |
|---|---|---|---|
| `devnest.pool.active.count` | Gauge | core | 活跃业务池数 `[现状已有]` |
| `devnest.pool.connection.usage` | Gauge | core | 各池连接使用率 |
| `devnest.tunnel.active` | Gauge | tunnel | 活跃隧道数 |
| `devnest.tunnel.reconnect.total` | Counter | tunnel | 重连累计次数 |
| `devnest.console.session.active` | Gauge | console | 活跃控制台会话数 |
| `devnest.console.ws.token.issued` | Counter | console | token 签发数 |
| `devnest.redis.pool.active` | Gauge | redis | 活跃 Redis 池数 |
| `devnest.pipeline.run.active` | Gauge | pipeline | 运行中流水线数 |
| `devnest.pipeline.run.duration` | Timer | pipeline | 流水线耗时 |
| `devnest.sql.execute.total` | Counter | datasource | SQL 执行次数(按结果标记) |
| `devnest.sql.execute.duration` | Timer | datasource | SQL 耗时 |

**演进提示**:未来若需 Prometheus 拉取,只需引入 `micrometer-registry-prometheus` 并暴露 `/actuator/prometheus`,**上述命名规范可直接复用,无需改造**。

### 4.4 观测维度三:健康

`[现状]` 无自定义 `HealthIndicator`,`/actuator/health` 不反映业务健康度。

`[目标]`:

| HealthIndicator | 检查内容 | 为什么需要 |
|---|---|---|
| `TunnelHealthIndicator` | 已配置跳板的连通性 | 隧道是全系统底座,底座挂了应立刻可见 |
| `PoolHealthIndicator` | 池使用率超阈值告警 | 连接耗尽的前兆 |
| `ResourceRegistryHealthIndicator` | 是否存在未登记 / 未释放资源 | §3.5 防线 1 的落地 |

注意:`PipelineRunManager` 等**不应**因业务运行失败而报 DOWN——健康端点反映"系统是否可用",不是"本次业务是否成功"。

### 4.5 观测维度四:日志关联(traceId)

`[现状]` 无 traceId,跨模块日志无法串联。

`[目标]`:

- 请求入口(HTTP filter)与 WS 握手处生成 `traceId`,写入 MDC;
- 日志 pattern 增加 `%X{traceId:-}`;
- `SensitiveDataLogFilter` 已存在,可作为实现载体;
- **异步任务需显式传递 MDC 上下文**——虚拟线程不继承 `InheritableThreadLocal`,这是最容易遗漏的点。

### 4.6 "监听维护"的完整答案

综合以上,运维在 `[目标]` 架构下可回答:

| 运维问题 | 手段 |
|---|---|
| 系统现在有哪些运行时资源? | `GET /actuator/resources` |
| 各类型资源各有几个? | 同上 `summary` |
| 隧道是否连通?连接池是否将耗尽? | `GET /actuator/health` |
| 各模块负载与吞吐如何? | `/actuator/metrics/*` |
| 一次操作横跨哪些模块? | 日志 traceId 串联 |
| 关闭是否干净? | 关闭报告 + 资源状态校验 |

且以上能力**对新增模块自动生效**,平台零改动。

## 5. 核心设计四:扩展点契约

### 5.1 先澄清:v1.0 的 `ToolModule` 为什么该砍

`架构文档` §0.2.1 把 `ToolModule` 缺失列为"能力缺失"。这个判定正确,但**补偿时机是 S3,不是 S2**。

原因:**一个扩展点在"没有第二个实现"时,是纯粹的抽象成本**——它增加理解负担,却不产生收益。S1 阶段五个业务模块各有职责,谁也不会替代谁,`ToolModule` 自然无消费者。

S3 的前提变了:`http`、`ai` 及未来工具接入时,"模块注册、生命周期启停、元信息治理"就有了**真实消费者**。

> **结论**:扩展机制应在 S3 建设。这是本文档对 `架构文档` §0.2.1 的**时序澄清**——它确实是能力缺失,但缺失的补偿时机是 S3。

### 5.2 关键设计原则:扩展点必须与治理联动

v1.0 的 `ToolModule`(`name`/`onStart`/`onShutdown`/`isEnabled`)即使补回来,也**依然是个空壳**——因为它与资源治理、可观测性毫无关系,实现者填四个方法却得不到任何平台能力。

**S3 的扩展点必须是"治理能力的接入契约"**:

```java
// core/tool/  [目标]
public interface DevNestTool {

    /** 元信息:名称、版本、所依赖的 core 能力 */
    ToolDescriptor descriptor();

    /** 本工具管理的运行时资源,供 ResourceRegistry 登记 */
    default Collection<ManagedResource> resources() { return List.of(); }

    /** 本工具的健康度,供聚合到 /actuator/health */
    default Health health() { return Health.unknown().build(); }

    /** 生命周期钩子(可选) */
    default void onStart() { }
    default void onStop() { }
}
```

**关键差异**:实现此接口后,工具**自动获得**——

- 其资源出现在 `/actuator/resources`;
- 其健康度进入 `/actuator/health`;
- 其生命周期被平台统一编排;
- 其身份在 SERVER 形态下自动按用户隔离。

**这才是一个有意义的扩展点**:它不是注册表,而是治理能力的接入方式。

### 5.3 注册与发现

`[目标]` `ToolRegistry` 通过 Spring 收集所有 `DevNestTool` 实现(与 `架构文档` §2.3 中 v1.0 设想一致),但**额外承担**:

## 7. 明确不做的事(边界声明)

架构作品必须写清"不做什么"。以下均为**经过考虑的否定**,而非遗漏:

| 不做 | 理由 |
|---|---|
| **分布式部署 / 集群** | 单实例 + DB 足以支撑目标场景(公司内网自用工具平台)。引入分布式会带来会话共享、一致性、部署复杂度,与"轻量工具"定位冲突 |
| **微服务拆分** | S2/S3 仍是**单进程多模块**。模块化解决的是开发期边界与可替换性,不是部署隔离。拆成微服务会让"一个平台装多个工具"变成运维负担 |
| **运行时热插拔 jar** | 工具在**构建期**接入。运行时装卸 jar 需要类加载器隔离、版本兼容治理,收益远小于成本 |
| **多租户(B2B SaaS 式)** | 只做"多用户共享一个实例",不做"多组织数据强隔离"。后者需要全表租户维度改造,非目标场景 |
| **`AbstractRoutingDataSource`** | `架构文档` §0.1 已论证:DevNest 是"多数据源并存、按 ID 取用",池工厂才是对的抽象 |
| **统一的资源释放编排** | §3.1 已论证:登记 ≠ 接管。释放仍自治,避免引入顺序与失败传播问题 |

## 8. 验收视角

本文档所述设计完成后,应满足:

| 验收项 | 验证方式 |
|---|---|
| 同一 jar 切换形态 | 两组启动参数,形态正确切换,**业务代码零改动** |
| 本地形态不退化 | LOCAL 形态端到端功能与 S1 **完全一致** |
| 服务端形态不静默失效 | 故意装配 `LocalUserProvider` → **启动失败**并给出明确原因 |
| 装配契约有效 | 外部新增 `TunnelPortForwarder` 实现 → 无需改 tunnel 模块即生效 |
| 资源可观测 | `GET /actuator/resources` 返回全部 9 类资源,数量与 `能力清单` §4 一致 |
| 漏登记可被发现 | 故意新增一个未登记的资源 → 启动告警 + 测试失败 |
| 平台零改动 | 新增一个工具模块 → 其资源/指标/健康**自动**出现在端点中 |
| 关闭可验证 | `/actuator/shutdown` 后,资源状态全部为 `RELEASED`,无残留 |

## 10. 落地顺序建议

本文档不规定时间,只规定**依赖顺序**(前项未完成,后项会以"硬编码 + 特例"完成,最终不可维护):

```
1. 形态元注解 + 默认 LOCAL                    ← 一切的前提
2. 三个 SPI 补装配契约                         ← 让"替换"真正可行
3. 防退化自检(不静默失效)                     ← 保护正确性
4. ResourceRegistry + 资源登记                  ← 治理基础
5. /actuator/resources + 指标 + 健康            ← 可观测落地
6. traceId                                     ← 可观测补全
7. 鉴权链路(按形态装配)                       ← 服务端前置
8. 状态归属隔离(会话/隧道/池/运行)             ← 多用户正确性
9. DevNestTool 扩展点契约                      ← S3 入口
```

第 1–3 项对应 `架构演进路线` §6 的**前置项**,是投入产出比最高的部分:改动集中在配置层与抽象层,**不触碰业务逻辑**。
