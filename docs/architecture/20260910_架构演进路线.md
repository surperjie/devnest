# DevNest 架构演进路线

> 版本:v1.0  日期:2026-09-10  作者:Ajiejiejie
> 配套文档:[20260910_当前实现能力清单.md](20260910_当前实现能力清单.md)(现状)、[20260910_目标架构.md](20260910_目标架构.md)(终态)

## 0. 为什么需要这份文档

`需求.md` 的定位是**单机自用工具**,§13 明确写着"不做多用户、不做外网服务、不做复杂权限"。而项目的新方向是:

1. **双形态**:本地单机运行 + 服务端多用户部署,**且要能快速切换**;
2. **长期形态**:像 DevNest(巢)一样,**集成多种开发工具的平台**;
3. **性质**:这是一个**架构设计作品**,设计意图的完整性与取舍的可解释性,与功能同等重要。

这不是推翻原有需求,而是**给原有需求加上"演进路径"这一维度**。`需求.md` 描述的是 **S1 阶段**的形态,它依然有效——只是不再是终点。

本文档的职责是:**定义阶段边界、每阶段的架构义务、以及不可退让的不变量**。它不描述功能清单(那是需求文档的事),只描述**架构上必须发生什么**。

## 1. 演进总纲

### 1.1 三个阶段

```
S1 单机自用(当前)
    │  特征:仅回环、单用户、无鉴权、桌面壳打包
    │  架构手段:物理分包 + 编译期边界
    │
    │  触发:S1 的形态已稳定,且需要"S2 的能力"
    ▼
S2 双形态(本地 / 服务端多用户)
    │  特征:同一套代码,两种装配;一个开关决定形态
    │  架构手段:装配层条件化 + 身份层抽象 + 状态归属
    │
    │  触发:S2 稳定,且有第二个"工具"要接入
    ▼
S3 工具巢穴(多工具集成平台)
       特征:工具可插拔,平台管治理,工具管业务
       架构手段:扩展点契约 + 资源治理 + 全局可观测
```

### 1.2 一句话概括每一阶段的架构本质

| 阶段 | 本质问题 | 关键动作 |
|---|---|---|
| S1 | "怎么在一台机器上把工具做出来" | 模块化(已完成) |
| S2 | "怎么让同一份代码在两种形态下都正确" | **装配层建设** |
| S3 | "怎么让第三个、第四个工具能低成本接进来" | **治理层建设** |

### 1.3 一条重要判断:S1 → S2 不是重写

当前代码的业务抽象**已经为 S2 做好了准备**:

- `CurrentUserProvider` 已定义(身份来源的抽象点)
- `V10` / `V11` 已加入 `operator` / `owner` / `visibility` 字段
- `DEVNEST_SERVER_ADDRESS` / `prod` profile / CORS 白名单已支持配置覆盖

**真正缺的不是业务抽象,而是"装配层"**——即:同一批接口,在本地形态装 `LocalXxx` 实现,在服务端形态装 `SessionXxx` 实现。这一层目前**完全不存在**(全库 `@ConditionalOn*` 数量为 0)。

**结论:S2 的主要工作量在配置层与安全层,不在业务层。** 这是本路线最重要的判断。

## 2. S1 —— 单机自用(当前状态)

### 2.1 形态定义

| 维度 | 取值 |
|---|---|
| 网络边界 | `127.0.0.1:38080`,仅回环 |
| 用户模型 | 单用户,无身份体系 |
| 用户标识 | `System.getProperty("user.name")` |
| 数据可见性 | 全量可见 |
| 部署方式 | Tauri 桌面壳以 sidecar 拉起 jar |
| 安全边界 | 绑卡 + CORS 白名单 + WS 一次性 token |

### 2.2 已完成的架构建设

| 建设 | 状态 | 说明 |
|---|---|---|
| 物理分包 | ✅ | 8 个 Maven 模块 |
| 编译期边界强制 | ✅ | `maven-enforcer-plugin`,违规即构建失败 |
| 依赖倒置 | ⚠️ | 2 个 SPI 接口,但无装配契约 |
| 资源自治释放 | ✅ | 9 处 `@PreDestroy`(清单见能力清单 §4) |
| 统一线程出口 | ✅ | `virtualExecutorService` |
| 两套连接池隔离 | ✅ | 配置库池 / 业务池 |

### 2.3 S1 的架构缺口

以下缺口**在 S1 形态下不构成故障**,但**是 S2 的阻塞项**:

| 缺口 | S1 下的表现 | S2 下的后果 |
|---|---|---|
| 无装配契约 | 三个 SPI 各只有一个实现,"恰好"能跑 | **换实现即启动失败** |
| 无身份体系 | 无影响 | **无法区分用户** |
| 内存态为全局单例 | 无影响 | **多用户共享状态,越权/串扰** |
| 无资源登记表 | 靠人工核对 | **运维无法查询资源,漏挂回调无人发现** |
| `LocalUserProvider` 取 OS 账号 | 值正确 | **所有记录归到同一个账号,静默失真** |

**S1 的退出判据**:无需改动即可稳定自用;**且**上述缺口已被识别并列入 S2 计划(即本文档成立)。

## 3. S2 —— 双形态(本地 / 服务端多用户)

### 3.1 形态定义

S2 的核心是**同一份构建产物,支持两种装配**:

| 维度 | 本地形态(Local) | 服务端形态(Server) |
|---|---|---|
| 绑定地址 | `127.0.0.1` | `0.0.0.0` 或内网网卡 |
| 用户模型 | 单用户 | 多用户 |
| 身份来源 | OS 账号 | 登录态(Session / Token) |
| 鉴权 | 无(靠边界收敛) | 完整鉴权链路 |
| 数据可见性 | 全量 | 按 `owner` / `visibility` 过滤 |
| 内存态归属 | 无归属(全局) | 按用户 / 会话隔离 |
| 配置库 | H2 或 MySQL | MySQL |
| 前端 | 桌面壳(Tauri) | 浏览器 |

### 3.2 "快速切换"的架构定义

"快速切换"必须有**可验收的判据**,否则会变成口号。本文档定义为:

> **切换形态不需要修改任何业务代码,不需要重新编译业务模块;仅通过启动参数(profile / 环境变量)决定装配结果。**

验收方式:同一个 jar,用两组不同的启动参数启动,形态正确切换,且:
- 本地形态下**功能与 S1 完全一致**(不因引入多用户能力而退化);
- 服务端形态下**身份、鉴权、数据隔离**全部生效。

### 3.3 S2 必须完成的架构动作

按依赖顺序排列(前面的不完成,后面的无法正确实现)。

#### 动作 1:装配层建设(其他动作的前提)

**问题**:当前所有 Bean 都是无条件注册,没有"形态"这一概念。

**做法**:
- 为每个可变实现定义形态条件(`@ConditionalOnProperty` 等);
- 引入自动配置机制(`AutoConfiguration.imports`),让模块**自描述**其 Bean,而不是被启动类无差别扫描;
- 三个 SPI 实现补 `@ConditionalOnMissingBean`,从"只能解耦"升级为"**默认可被覆盖**"。

**验收**:新增一个替代实现,无需改动提供方模块代码即可生效。

#### 动作 2:身份层建设

**问题**:`LocalUserProvider` 的前提("仅绑回环")在服务端形态下失效,且会**静默写错数据**。

**做法**:
- 服务端形态提供基于登录态的 `CurrentUserProvider` 实现;
- **当前提被打破时必须有防护**:服务端形态下若仍装配了 `LocalUserProvider`,应**启动即失败**而非静默运行;
- 这是"隐含假设失效"的防御——比新增功能更重要。

**验收**:服务端形态下,不同用户操作写入不同的 `owner` / `operator`。

#### 动作 3:状态归属建设

**问题**:以下组件持有**进程内全局状态**,在服务端形态下会被多用户共享:

| 组件 | 状态 | 风险 |
|---|---|---|
| `ConsoleSessionManager` | `Map<wsSessionId, ConsoleSession>` | 不校验属主,可操作他人会话 |
| `SshTunnelManager` | `Map<Long, SshTunnelInstance>` | 隧道全局共享,无归属 |
| `PortAllocator` | `Set<Integer>` 已分配端口 | 并发下有 TOCTOU 竞态 |
| `PipelineRunManager` | `Set<Long>` + `Semaphore` | 全局并发闸门,非按用户 |

**做法**:明确每个状态的**归属维度**(全局 / 用户 / 会话),并落实校验;`PortAllocator` 需修复竞态(探测与占位需原子)。

**验收**:用户 A 无法观察到、操作到用户 B 的会话与运行。

#### 动作 4:鉴权链路建设

**问题**:业务 API **全裸**;`ActuatorSecurityConfig` 只保护 Actuator 端点。

**做法**:
- 服务端形态引入完整鉴权;
- 本地形态**必须保持零配置可用**(不能因为加了鉴权就要求本地也登录)。

**这是"双形态"最容易做砸的地方**:常见的失败是"为了服务端安全,把本地体验也拖下水"。验收标准里"本地形态功能与 S1 完全一致"就是防这个。

#### 动作 5:资源治理与可观测性建设

**问题**:见 `当前实现能力清单` §6.2。

**做法**:见 `目标架构`。这一动作在 S2/S3 之间可以**渐进完成**,但应**尽早开始**——因为它同时是 S3 的基础。

### 3.4 S2 的完成判据

- [ ] 同一 jar,两组启动参数,形态正确切换,业务代码零改动;
- [ ] 本地形态端到端功能与 S1 **完全一致**;
- [ ] 服务端形态下身份、鉴权、数据隔离全部生效;
- [ ] 服务端形态下**不存在静默失效**(身份缺失、归属缺失必须显式失败);
- [ ] 三个 SPI 均可被外部实现替换,无需改提供方代码;
- [ ] 资源清单可被运行时查询,而非人工核对。

## 4. S3 —— 工具巢穴(多工具集成平台)

### 4.1 形态定义

DevNest 的"nest"含义在 S3 才真正兑现:

- 平台提供**治理能力**(资源、可观测、身份、扩展点);
- 工具提供**业务能力**(HTTP 调试、AI 辅助、以及未来接入的工具);
- 新增工具**不需要改动平台代码**。

### 4.2 S3 必须完成的架构动作

#### 动作 1:扩展点契约

**这里需要澄清一个关键问题**:v1.0 曾设计 `ToolModule` SPI,实现时被放弃,`架构文档` §0.2.1 将其列为"能力缺失"。

**放弃是对的,但理由不是"不需要",而是"当时没有消费者"**:

> 一个扩展点在**没有第二个实现**时,是纯粹的抽象成本——它增加了理解负担,却不产生任何收益。`ToolModule` 在 S1 阶段正是如此:五个业务模块各有职责,谁也不会替代谁。

**S3 的前提变了**:当 `http`、`ai` 以及未来的工具要接入时,"模块注册、生命周期启停、元信息治理"就有了**真实消费者**。

**因此:扩展机制应在 S3 建设,而不是在 S2 或更早。** 这是本文档对 `架构文档` §0.2.1 的一处**时序澄清**——它确实是能力缺失,但缺失的补偿时机是 S3。

#### 动作 2:资源治理层(统一登记)

**这是 S1/S2/S3 贯穿的主题,但只有在 S3 才必须完整**:

- v1.0 的 `ResourceRegistry` 目标是"统一登记 + 逆序释放";
- `架构文档` §4.3 曾论证"各模块自治是对的"(理由是资源类型多样,统一治理反而要处理顺序与失败)。

**两处结论看似冲突,实际可以调和**:

| 职责 | 归属 | 理由 |
|---|---|---|
| **释放执行** | 各模块自治 | 模块最了解自己的资源,失败也不牵连他人 |
| **登记与可见** | 统一登记表 | 运维需要一个"总账",否则无法查询、无法审计遗漏 |

即:**登记 ≠ 接管释放**。资源在登记表注册自己,释放仍由各模块的 `@PreDestroy` 执行,登记表负责提供**全局视图与遗漏检测**。

这个调和方案是 S3 资源治理的设计前提,详见 `目标架构`。

#### 动作 3:全局可观测性

平台必须能回答"**现在系统里有什么、在跑什么、健康吗**",且答案覆盖**所有模块**,包括未来接入的工具。

这与用户的诉求直接对应:"后续如果要监听维护能获取到所有模块数据"。

### 4.3 S3 的完成判据

- [ ] 新增一个工具模块,平台代码零改动;
- [ ] 该工具的运行时资源自动出现在全局资源视图中;
- [ ] 该工具的指标自动进入指标端点;
- [ ] 该工具的生命周期由平台统一编排(启停、健康、释放);

## 5. 演进不变量(任何阶段都不可退让)

从 `需求.md` §13 提炼,并结合新方向补充:

| # | 不变量 | 来源 | 说明 |
|---|---|---|---|
| 1 | **依赖单向** | 架构文档 §2.1 | 业务模块之间零依赖,横向协作一律经 `core/spi` |
| 2 | **边界编译期强制** | 架构文档 §0.5 | 违规依赖必须构建失败,不能只靠约定 |
| 3 | **配置库与业务资源物理隔离** | 架构文档 §1 | 两套连接池,事务不串 |
| 4 | **敏感数据加密 + 响应脱敏** | 需求 §2.1 | 任何阶段不得回退 |
| 5 | **资源必须显式释放** | 需求 §2.2 | 新增资源必须同步登记(能力清单 §4) |
| 6 | **AI 永远辅助,手动永久兜底** | 需求 §13 | AI 失效不得影响手动能力 |
| 7 | **本地形态可用性不被牺牲** | 本文档新增 | 引入服务端能力**不得**要求本地登录/配置 |
| 8 | **不静默失效** | 本文档新增 | 前提被打破时必须显式失败,而非继续运行 |

> 第 7、8 条是本次演进新增的不变量,专为防止"为了 S2 而破坏 S1"。
> 这两条对应的典型反例分别是:为服务端安全导致本地也需登录(违反 7);`LocalUserProvider` 在服务端静默写错 `owner`(违反 8)。

## 6. 当前距离 S2 的差距清单

按"阻塞程度"排序,可直接作为 S2 的待办来源。

| # | 差距 | 阻塞什么 | 对应动作 |
|---|---|---|---|
| 1 | 全库 `@ConditionalOn*` = 0,无形态概念 | 一切切换 | 动作 1 |
| 2 | 三个 SPI 无装配契约,换实现即冲突 | 身份层、扩展点 | 动作 1 |
| 3 | `LocalUserProvider` 服务端静默失真 | 身份正确性 | 动作 2 |
| 4 | 业务 API 无鉴权 | 服务端安全性 | 动作 4 |
| 5 | 内存态全局共享,无归属校验 | 多用户隔离 | 动作 3 |
| 6 | `PortAllocator` TOCTOU 竞态 | 并发正确性 | 动作 3 |
| 7 | 无资源登记表 | 运维可见性 | 动作 5 |
| 8 | 无业务指标 / HealthIndicator | 运维可见性 | 动作 5 |
| 9 | `visibility` 字段无过滤逻辑 | 数据隔离 | 动作 3 |

> 第 1、2 项是**前置项**:它们不解决,S2 的其余动作都会以"硬编码 + 特例判断"的方式完成,最终变成无法维护的形态判断散落各处。
