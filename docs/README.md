### L1 的两份文档如何分工

现状层有两份文档,职责不同,**不要混用**:

- `架构文档` 回答"**机制是怎么设计的**"——描述设计意图与实现方案;
- `当前实现能力清单` 回答"**现在到底有什么能用**"——逐模块判定 ✅/⚠️/❌。

典型差异:`架构文档` §4.7 会说明缓存设施"声明了 3 个 Caffeine 缓存",而 `能力清单` 会把它标为 ⚠️ 半实现,因为**没有任何业务代码使用**。"代码里有"不等于"功能能用"。

### L2 的两份文档如何分工

演进层有两份文档,职责不同,**不要混用**:

- `架构演进路线` 回答"**架构上必须发生什么**"——定义 S1→S2→S3 的阶段边界与每阶段的架构义务(战略);
- `目标架构落地路线图` 回答"**具体怎么做、什么顺序、怎么验**"——P0–P5 的任务/落点/门禁/风险/规模(执行)。

典型差异:`架构演进路线` 说"S2 必须完成装配层建设"(义务),而 `落地路线图` 说"P1 任务 1.1–1.6、前置 P0、出口判据是三组启动参数"(可执行)。**战略不写任务,执行不重述终态。**

## 权威性约定

同一问题在多份文档出现不同结论时:

| 问题类型 | 以谁为准 |
|---|---|
| 机制如何设计 | `20260910_架构文档.md` |
| 某个能力是否可用 | `20260910_当前实现能力清单.md` |
| 演进阶段与阶段义务 | `20260910_架构演进路线.md` |
| 终态设计 | `20260910_目标架构_v2.0.md` |
| 执行计划、阶段顺序与门禁 | `20260910_目标架构落地路线图.md` |
| 数据表结构 | Flyway 脚本(`backend/devnest-boot/src/main/resources/db/migration`) |
| 接口行为 | 实际代码 |
| 怎么跑、怎么排障 | `wiki/`(发布后的 GitHub Wiki) —— 只做导航与操作,不重述设计结论 |

## 重要说明

**架构文档以 `20260910_架构文档.md` 为准。**

v1.0 设计稿中描述的 `ToolModule` SPI、`ResourceRegistry`、`ShutdownHook`、`DynamicDataSourceManager`
等抽象从未落地,包结构、端口、Redis 客户端等描述也与实际代码不符。该文档原样保留,
仅作设计演进的历史记录,请勿据此理解现有代码。

`20260910_架构文档.md` 第 0 节列出了 v1.0 与实现之间的**全部已知差异**,第 10 节列出了**已知技术债**。

### 关于"多用户"的口径

`需求.md` §13 明确写着"不做多用户、不做外网服务"。该结论描述的是 **S1 单机形态**,依然有效。
项目的新方向——**本地运行与服务端多用户场景快速切换**——属于 **S2 阶段**,详见
[架构演进路线](architecture/20260910_架构演进路线.md)。

这不是矛盾,而是**阶段差异**:`需求.md` 描述 S1,演进路线描述如何到达 S2/S3。

## Wiki

`wiki/` 是 GitHub Wiki 的**页面源文件**。Wiki 的定位是**入口与操作手册**,不承担权威性:
它只做导航与操作步骤,**不复制本目录下文档的设计结论** —— 否则等于同一个问题给出两个答案。

- 改 Wiki = 改 `wiki/*.md` 并提 PR(走正常评审,可回溯、可回滚)
- 发布 = `.\scripts\sync-wiki.ps1`(镜像 `.md` 页面到 GitHub Wiki,孤儿页会被删除)
- **不要直接在 GitHub 网页上编辑 Wiki 页面** —— 下次发布会把它覆盖掉
- 首次发布前,需在仓库 Settings 启用 Wikis 并手工创建第一个页面(GitHub 才会生成 `.wiki.git` 仓库)
