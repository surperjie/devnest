# 贡献指南

## 1. 分支模型

| 分支 | 角色 | 说明 |
|---|---|---|
| `dev` | **开发主线** | 日常提交都在这里；CI 每次都跑质量门禁 |
| `main` | **发布镜像** | 只接受来自 `dev` 的快进合并（`git merge --ff-only dev`），内容与 `dev` 保持一致 |

发版在 `main` 上打 `v*` 标签，详见 [CI 与发布](CI与发布)。

---

## 2. 提交前必须过的门禁

**合并的前提是 CI 全绿**。本地能先跑就跑一遍，别把红灯留给流水线：

```powershell
# 后端：单测 + 集成测试 + enforcer + ArchUnit + JaCoCo
cd backend
mvn -B verify

# 增量行覆盖率（先 verify 产出 jacoco.xml，再判定）
cd ..
.\scripts\check-incremental-coverage.ps1 -BaseRef origin/dev -ShowDetail
```

门禁细节见 [质量门禁](质量门禁)。几条容易踩的：

| 约束 | 由谁拦 |
|---|---|
| 业务模块之间横向依赖 | `maven-enforcer`（`validate` 阶段直接失败） |
| 新增运行时资源（线程池 / 连接池 / 缓存）未登记 | `ResourceRegistry` 启动自检 + 测试基座 |
| 用 `@ConditionalOnProperty` 裸写形态分支 | ArchUnit |
| `@Deprecated` 未带 `since` | ArchUnit |
| 新增行没被测试覆盖 | 增量覆盖率门禁（≥ 80%） |
| 引入 CVSS ≥ 7 的依赖 | OWASP dependency-check |

> **不要为了过门禁降低门禁。** 把阈值调低、把违规文件加进排除清单、把代码改成注释，都不是修复 —— 那是把约束变成愿望。

## 3. 提交信息

采用 **Conventional Commits**，描述用中文：

```text
<type>(<scope>): <简短描述>

<为什么这么改 —— 现象、根因、取舍>
```

常用 `type`：`feat` / `fix` / `refactor` / `test` / `docs` / `chore` / `build` / `ci`。`scope` 用模块名或领域，如 `tunnel`、`datasource`、`ci`、`docs`。

> 正文重点写**根因与取舍**，而不是复述 diff。半年后回来看的是"当时为什么这么选"。

## 4. 新增一个工具模块（扩展判据）

项目的第一性判据是 **「新增一个工具模块，平台代码改动 = 0」**，而且是**机器可验**的。加模块时按这个顺序走：

1. 在 `backend/` 下建模块，只依赖 `devnest-core`（横向依赖会被 enforcer 拦）；
2. 通过 `core.spi` 暴露能力，**不修改 `devnest-boot` 之外的平台代码**；
3. 在 `devnest-boot` 里完成装配（这是唯一允许改的平台模块）；
4. 表结构走新的 Flyway 迁移脚本，不改历史脚本；
5. 补测试到增量覆盖率门禁能过；
6. 更新 [当前实现能力清单](https://github.com/surperjie/devnest/blob/main/docs/architecture/20260910_当前实现能力清单.md)。

**如果为了让新模块跑起来不得不改平台代码，先停下来** —— 那说明扩展点缺失，应该先补扩展点，而不是把特例写进平台。

## 5. 文档约定

- 命名：`YYYYMMDD_主题.md`
- **每个问题只有一份权威文档**，新增/调整后必须同步更新 [`docs/README.md`](https://github.com/surperjie/devnest/blob/main/docs/README.md) 索引，并说明它在四层体系中的位置（见 [文档地图](文档地图)）
- 描述实现时要区分「**代码里有**」和「**功能能用**」—— 后者以能力清单的 ✅ / ⚠️ / ❌ 判定为准
- 已过时的设计稿不删除，但要在索引里标注**已归档 / 不反映实现**

## 6. Wiki 维护

Wiki 源文件在 `docs/wiki/`，发布脚本 `scripts/sync-wiki.ps1`。

```powershell
# 预览将同步哪些文件（不写远端）
.\scripts\sync-wiki.ps1 -WhatIf

# 发布
.\scripts\sync-wiki.ps1
```

**不要直接在 GitHub 网页上编辑 Wiki 页面** —— 下次发布会被 `docs/wiki/` 的内容覆盖。改 Wiki 的正确姿势是改 `docs/wiki/*.md` 并提 PR。

Wiki 的定位是**入口与操作手册**，不承担权威性；权威内容永远在 `docs/`（见 [文档地图](文档地图)）。
