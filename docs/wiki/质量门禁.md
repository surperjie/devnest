# 质量门禁

> **没有执行者的约束不是约束，是愿望。**
>
> 本页只讲「怎么用、怎么排障」；门禁的设计理由与约束矩阵的完整版本见
> [目标架构 v2.0 §5](https://github.com/surperjie/devnest/blob/main/docs/architecture/20260910_目标架构_v2.0.md)。

---

## 1. 后端构建 = `mvn verify`，不是 `package -DskipTests`

这是整个门禁体系的地基：**测试必须真的被执行**，否则 ArchUnit、覆盖率、Testcontainers 全都失去载体。

```powershell
cd backend
mvn -B verify
```

`verify` 一次跑完这几件事：

| 门禁 | 执行者 | 触发阶段 | 阈值 |
|---|---|---|---|
| 单元测试 | Surefire | `test` | 失败即红 |
| 集成测试 | Failsafe + **Testcontainers**（真实 MySQL / Redis 容器） | `verify` | 失败即红 |
| 依赖边界 · 版本收敛 | `maven-enforcer` | `validate` | 违规即红 |
| 分层依赖 · 形态语义 · 弃用标注 | **ArchUnit** | `test` | 违规即红 |
| 覆盖率地板 | **JaCoCo** `check` | `verify` | 见 §2 |
| 增量行覆盖率 | [`scripts/check-incremental-coverage.ps1`](https://github.com/surperjie/devnest/blob/main/scripts/check-incremental-coverage.ps1) | CI / 本地 | **≥ 80%** |
| 已知高危依赖 | **OWASP dependency-check**（`-Psecurity-scan`） | `verify` | CVSS ≥ 7 即红 |

> 没有 Docker 时，Testcontainers 用例会**显式 skip**（不是静默通过），其余测试照常执行。

## 2. 两层覆盖率门禁，各管一段

| 门禁 | 管什么 | 特性 |
|---|---|---|
| JaCoCo `check`（棘轮地板） | **存量**覆盖率不允许下降 | 阈值只升不降 |
| 增量行覆盖率门禁 | **本次改动引入的、可执行却没被覆盖的行** | 只卡变更行，不让历史旧账变成永久红灯 |

把两者分开的原因很直接：**存量覆盖率一时半会补不上来，但"从今天起新增的代码必须被测"是可以立刻做到的**。如果只有一道全量门禁，它要么长期为红（等于没有门禁），要么阈值被压低（等于没有约束）。

### 增量门禁的工作方式

1. 取基线 `BaseRef`，用 `git diff` 得到**本次改动的行号**（按文件分组）；
2. 未跟踪（还没 `git add`）的新文件按「整个文件都是新增」处理；
3. 读该模块的 `target/site/jacoco/jacoco.xml`，取出每个源文件的**可执行行**及其覆盖状态；
4. 判定对象 = 改动行 ∩ 可执行行（注释、空行、import 不计入分母）；
5. `增量行覆盖 = 覆盖行 / 可执行改动行`，低于阈值即失败，并打印每个文件的明细与未覆盖行号。

### 基线过远保护（重要）

基线取 `github.event.before`。**把长期分支快进合并进 `main` 时，它会把「分支晋升」误判成「一次增量提交」**：`before` 还停在几十个提交之前，"本次改动"于是退化成"整个分支历史"，增量门禁随之退化成**存量全量门禁**（实测 22.6%，必然长期为红）。

脚本因此内置两道保护，任一命中即回退到 `HEAD~1` 并打印 `::notice::`：

| 参数 | 默认 | 含义 |
|---|---|---|
| `-MaxBaselineCommits` | `15` | `BaseRef..HEAD` 提交数超过该值即认为基线过远 |
| `-MaxBaselineFiles` | `60` | `backend` 下改动文件数超过该值即认为基线过远 |

设为 `0` 可关闭对应判定。

> 回退是**被宣布的降级**，不是静默放行 —— 门禁的输入（几个提交、几个改动文件、实际用了哪条基线）每次都打印出来。

### 未被判定的文件会被显式列出

若某个模块本次**没有产出覆盖率报告**（典型原因：该模块一个测试都没有），该模块下的改动文件会被跳过，脚本会明确打印「多少个文件、分别是哪个模块」。

这仍然是个真实的约束缺口 —— **门禁对这批改动没有约束力**，只是不再被静默掩盖。给这些模块补测试才是根治。

## 3. 本地怎么跑增量门禁

先让 `jacoco.xml` 存在（门禁读的是报告，不是源码），再跑脚本：

```powershell
# 1) 先构建一次，产出 backend/**/target/site/jacoco/jacoco.xml
cd backend
mvn -B verify

# 2) 再判定：基线一般取分支分叉点或 origin/dev
cd ..
.\scripts\check-incremental-coverage.ps1 -BaseRef origin/dev -ShowDetail
```

常用参数：

| 参数 | 说明 |
|---|---|
| `-BaseRef <ref>` | **必填**。基线 ref，如 `origin/dev`、`HEAD~1`、某个 sha |
| `-Threshold 0.80` | 覆盖率阈值，与 `backend/pom.xml` 的 `jacoco.incremental.floor` 保持一致 |
| `-ShowDetail` | 打印每个文件的未覆盖行号、被跳过的文件 |
| `-MaxBaselineCommits` / `-MaxBaselineFiles` | 基线过远保护阈值，见 §2 |
| `-RepoRoot` / `-ModulesRelativePath` | 仓库根与模块目录，默认自动推断 |

**退出码**：`0` = 通过；`1` = 未达标或基线 ref 不存在。

### 输出怎么读

```text
基线范围        : 29 个提交, backend 下改动文件 167 个
基线过远,已回退到 HEAD~1 —— 本次按"增量提交"判定,而不是"整个分支历史"。
     5.8%  (23/397)  backend/devnest-datasource/src/main/java/.../DatabaseQueryServiceImpl.java
增量行覆盖: 22.6%  (332/1472)
门禁未通过:增量行覆盖率 22.6% 低于要求的 80%。
```

一行一个文件，`覆盖行/可执行改动行`。**只补测试，不要为了过门禁把行改成注释或加 `@Generated`** —— 那等于把约束变成愿望。

## 4. 新增代码怎么过门禁

| 你做了什么 | 需要补什么 |
|---|---|
| 新增 Service / 工具方法 | 单测覆盖到主要分支（含异常分支） |
| 新增 Controller / DTO 映射 | 接口测试或 mapper 单测 |
| 新增跨模块依赖 | **不行** —— `maven-enforcer` 会直接让构建失败，改用 `core.spi` 契约 |
| 新增运行时资源（线程池 / 连接池 / 缓存） | 走 `ResourceRegistry` 登记 + 测试基座，启动自检会校验 |
| 用 `devnest.mode` 做形态分支 | 不要裸写 `@ConditionalOnProperty`，ArchUnit 会拦 |
| 标注 `@Deprecated` | 必须带 `since` 参数，ArchUnit 会拦 |
| 新增依赖 | 需通过版本收敛 + 无 CVSS ≥ 7 漏洞 |

## 5. 排障速查

| 现象 | 原因 | 处理 |
|---|---|---|
| 门禁报「无判定对象，按通过处理」 | 本次改动只碰了注释 / 空行 / import / 测试代码 / 纯配置 | 正常，无需处理 |
| 大量文件显示 `[skip] 覆盖率报告中无此类` | 该模块没跑测试，没产出 `jacoco.xml` | 给该模块补测试；或先用 `-ShowDetail` 确认 |
| 同一次提交在 `main` 上红、`dev` 上绿 | 基线过远（分支晋升被当成增量） | 应已由 §2 的保护吸收；若仍复现，检查两个 `-MaxBaseline*` 阈值 |
| 本地跑脚本全 `[skip]` | 还没构建，`jacoco.xml` 不存在 | 先 `mvn -B verify` |
| `We couldn't find remote ref` | `BaseRef` 不存在（没 fetch / 分支名写错） | `git fetch` 后重试 |
| OWASP 门禁显示「未执行」 | 缺 `NVD_API_KEY` | 见 [CI 与发布](CI与发布) |
